1 Estrategia y convención de código (que se corrige)
De dónde sale esta guía, y qué NO tiene
De las clases teóricas de la cátedra (Lic. Gustavo Bianchi) y de las 9 guías de ejercicios de la Cátedra Azcurra, las más nuevas etiquetadas Guía 2024_v2 y 2025_v1.

No hay parciales reales en el material de la cátedra, así que esta guía no los simula: se construye sobre las guías de ejercicios, que son el material con el que efectivamente se entrena y se evalúa. Cualquier "parcial modelo" que vieras acá sería inventado, y preferimos no hacerlo.

La convención de código es normativa, no una sugerencia

La cátedra publica un documento de estilo de codificación en C y corrige con él. Es la forma más barata de perder puntos: el algoritmo puede estar perfecto y el código mal presentado.

La dependencia que importa
Punteros es la unidad bisagra: sin entenderla no se puede pasar un parámetro por referencia (unidad 4), ni entender por qué un arreglo "se modifica solo" al pasarlo a una función (unidad 5), ni manejar archivos ni memoria dinámica. Si algo se te está haciendo difícil más adelante, casi siempre el agujero está acá.

Cómo estudiar esta materia

Programar, no leer
Es una materia de hacer. Leer soluciones da una falsa sensación de dominio: el código ajeno siempre se entiende. La prueba real es escribirlo desde cero con la hoja en blanco.

Método: leé la consigna, cerrá la guía, escribilo, y recién ahí compará. Lo que no te salió sin mirar es exactamente lo que todavía no sabés.
Trazá a mano antes de compilar
Las preguntas de "¿qué imprime este programa?" no se resuelven ejecutando: se resuelven siguiendo el valor de cada variable renglón por renglón, en papel. Hacelo aunque tengas el compilador al lado — es la habilidad que se evalúa.

El único caso donde printf y scanf NO usan lo mismo
Para un double: en printf podés usar %f o %lf, pero en scanf es obligatorio %lf. Si leés un double con %f, escribís sólo la mitad de la variable y el valor queda basura.

Entrada y salida

/* scanf necesita la DIRECCIÓN de la variable: por eso el & */
int edad;
float sueldo;

printf("Ingrese edad: ");
scanf("%d", &edad);        /* %d o %i para int */
scanf("%f", &sueldo);      /* %f para float; para double va %lf */
Olvidar el & en scanf
scanf("%d", edad) le pasa el valor de edad como si fuera una dirección de memoria. El programa compila (con warning) y al ejecutarse escribe en una dirección arbitraria: violación de segmento o, peor, pisado silencioso de otra variable.

La única excepción: con %s sobre un arreglo no va &, porque el nombre del arreglo ya es la dirección.
El Enter que queda en el buffer
Después de un scanf("%d", &n), el \n del Enter queda sin consumir. Si el siguiente scanf es %c, se come ese \n y parece que "no esperó". Solución: scanf(" %c", &letra) — el espacio antes del %c descarta los blancos pendientes.

La división entera es el error silencioso número uno
5 / 2 da 2, no 2.5, porque los dos operandos son int. Y guardar el resultado en un float no lo arregla: la cuenta ya se hizo mal antes de asignar.

Se arregla de dos formas: escribiendo una constante con punto (5.0 / 2) o casteando ((float)a / b). El casteo va sobre un operando, no sobre el resultado: (float)(a / b) sigue dando 2.

Pre y post incremento · lo que realmente pasa

int a = 5;
printf("%d", a++);    /* imprime 5, y DESPUÉS a pasa a valer 6 */
printf("%d", ++a);    /* a pasa a valer 7, y ENTONCES imprime 7 */
La regla en una línea
La diferencia está en qué valor devuelve la expresión, no en qué queda en la variable: en los dos casos la variable termina incrementada. a++ devuelve el valor viejo; ++a devuelve el nuevo.

Booleanos

#include <stdbool.h>      /* hace falta incluirlo: bool no es nativo de C */

Sin stdbool.h, la alternativa que muestra la cátedra es un enumerado: typedef enum {false, true} bool;

3 Control de flujo · Condicionales y ciclos

Elegir entre if encadenado y switch

El criterio es qué comparás
Rangos (nota >= 7, x < 0) → if / else if / else.
Valores discretos de un int o un char (mes 1..12, opción de menú) → switch. 
switch (mes) {
    case 1:
        printf("Enero");
        break;              /* sin el break, cae en cascada al siguiente case */
    case 2:
        printf("Febrero");
        break;
    default:
        printf("Inexistente");
}
El break olvidado
Sin break, la ejecución sigue hacia los case siguientes (fall-through) y se imprimen varios mensajes. La única caída legítima es apilar case sin código entre ellos, cuando varios valores comparten la misma acción.
Chequeo que detecta los dos errores clásicos
Probá los bordes: el mínimo válido, el máximo válido, uno menos y uno más. Cada corrida tiene que imprimir exactamente un mensaje.
· Imprime dos → te falta un else o un break.
· No imprime ninguno → te falta el default o el else final.

Validación de un dato · el molde del do-while

do {
    printf("Ingrese la altura (mayor a 0): ");
    scanf("%f", &altura);
    if (altura <= 0) {
        printf("ERROR: la altura debe ser mayor a 0.\n");
    }
} while (altura <= 0);      /* la condición es la del dato INVÁLIDO */
La verificación de una línea
Negá la condición del while: te tiene que quedar exactamente la definición de "dato correcto" del enunciado. Si negás altura <= 0 te queda altura > 0 ✔.

Cuando el ciclo termina, la variable ya tiene un valor válido garantizado: de ahí en adelante no hace falta volver a chequear.

Serie con centinela · el molde completo

suma = 0;
cantidad = 0;

printf("Ingrese un valor (0 para terminar): ");   /* LECTURA ANTICIPADA */
scanf("%d", &dato);

while (dato != 0) {
    if (cantidad == 0) {          /* el primer dato inicializa mayor y menor */
        mayor = dato;
        menor = dato;
    } else if (dato > mayor) {
        mayor = dato;
    } else if (dato < menor) {
        menor = dato;
    }
    suma = suma + dato;
    cantidad++;

    printf("Ingrese un valor (0 para terminar): ");   /* VOLVER A LEER */
    scanf("%d", &dato);
}

if (cantidad == 0) {
    printf("No se ingresaron datos.\n");             /* evita dividir por cero */
} else {
    printf("Promedio: %.2f\n", (float)suma / cantidad);
}
Inicializar mayor y menor en 0
Es el error más caro de este molde. Si la serie es −4, −9, el mínimo te va a dar 0, que ni siquiera está entre los datos. Inicializá con el primer dato, no con 0.

Prueba obligatoria: corré con una serie de todos negativos. Si el mínimo da 0, tenés este bug.
Olvidar la segunda lectura
Si la última línea del cuerpo del while no vuelve a pedir el dato, la condición nunca cambia: ciclo infinito. La lectura aparece dos veces en el molde y las dos son necesarias.
Dividir sin chequear que haya datos
Si el usuario ingresa el centinela de entrada, cantidad vale 0 y el promedio es una división por cero. El if (cantidad == 0) del final no es un adorno.

Ciclos anidados · dibujos y tablas

/* Triángulo de asteriscos: la fila i tiene i asteriscos */
for (fila = 1; fila <= n; fila++) {
    for (columna = 1; columna <= fila; columna++) {   /* depende de la fila */
        printf("*");
    }
    printf("\n");        /* el salto va en el ciclo EXTERNO, después del interno */
}
Chequeo de ciclos
Calculá a mano cuántas iteraciones hacen n = 1 y n = 2 y compará con tu código. El error clásico —una iteración de más o de menos— se ve ahí y en ningún otro lado.

Molde: for (i = 1; i <= n; i++) cuando el enunciado dice "los n primeros"; for (i = 0; i < n; i++) cuando pensás en posiciones de un arreglo.

Descomponer un número en dígitos

resto = numero;                   /* copia: el ciclo destruye la variable */
while (resto > 0) {
    digito = resto % 10;          /* último dígito */
    /* ... procesar el dígito ... */
    resto = resto / 10;           /* lo descarta. SIN esto: ciclo infinito */
}

4 Funciones y programación modular
Ésta es la unidad bisagra de la materia
Todo lo que viene después (arreglos, cadenas, structs, archivos, memoria dinámica) se apoya en entender pasaje por valor vs. por referencia. Si algo se te complica más adelante, el agujero casi siempre está acá.

Las tres partes de una función

#include <stdio.h>

float promediar(int nota_1, int nota_2);      /* 1. PROTOTIPO: antes del main */

int main()
{
    printf("%.2f\n", promediar(7, 10));       /* 3. LLAMADA */
    return 0;
}

float promediar(int nota_1, int nota_2)       /* 2. DEFINICIÓN */
{
    return (float)(nota_1 + nota_2) / 2;
}

Por valor vs. por referencia · la tabla que hay que tener grabada

Por valorPor referencia
Qué se entregaUna copia del valorLa dirección de memoria
MemoriaActual y formal usan distintas posicionesUsan la misma posición

El actual se modificaNOSÍ
Para quéEntradas que la función sólo leeSalidas: devolver más de un valor
ArreglosSiempre por referencia, y sin escribir & ni *
/* Por valor: NO funciona para modificar */
void duplicar_mal(int n)
{
    n = n * 2;              /* toca la copia local; num afuera no cambia */
}

/* Por referencia: SÍ funciona */
void duplicar_bien(int *n)
{
    *n = *n * 2;            /* el * desreferencia: escribe en la variable original */
}

int main()
{
    int num = 5;
    duplicar_mal(num);      /* num sigue valiendo 5 */
    duplicar_bien(&num);    /* ahora num vale 10 */
    return 0;
}
El bug invisible: esperar que una función modifique un parámetro por valor
No hay error de compilación ni crash: el programa simplemente no hace nada, y eso es lo que lo vuelve difícil de encontrar. Si una función tiene que devolver algo y ya usás el return para otra cosa, ese parámetro va por referencia.
Poner & cuando el parámetro YA es un puntero
Dentro de void leer(int *a), escribir scanf("%d", &a) pasa la dirección del puntero, no la de la variable original. scanf pisa el puntero con el número leído y el próximo *a apunta a cualquier lado.

Adentro de esa función va scanf("%d", a) — sin &, porque a ya es la dirección.

Programación modular

Una función, una responsabilidad
El molde que espera la cátedra: una función que lee, una que calcula y una que muestra. El main queda como coordinador y se lee de un vistazo.

Señal de que una función hace de más: si al nombrarla tenés que usar un "y" (leer_y_validar_y_mostrar), son tres funciones.

/* Recorrido de un vector: SIEMPRE i < n, nunca i <= n */
for (i = 0; i < n; i++) {
    scanf("%d", &vec[i]);      /* ojo: acá el & SÍ va, porque vec[i] es un int */
}

/* Matriz: el ciclo externo recorre filas, el interno columnas */
for (fila = 0; fila < FILAS; fila++) {
    for (columna = 0; columna < COLUMNAS; columna++) {
        printf("%4d", mat[fila][columna]);
    }
    printf("\n");
}

/* Diagonal principal: fila == columna, un solo ciclo */
for (i = 0; i < N; i++) {
    suma = suma + mat[i][i];
}
El off-by-one: <= en vez de <
for (i = 0; i <= n; i++) toca vec[n], que ya no pertenece al arreglo. C no controla los índices: en ejecución se escribe encima de lo que esté al lado en la pila — muchas veces la propia i, lo que genera un ciclo infinito.

El último índice válido de un arreglo de N elementos es N−1.
Un arreglo NO se copia ni se compara con = y ==
v1 = v2 ni siquiera compila. if (v1 == v2) sí compila, pero compara direcciones: da falso aunque los contenidos sean idénticos.

Hay que copiar y comparar elemento por elemento con un for.
Por qué los arreglos "se modifican solos"
El nombre de un arreglo ya es la dirección de su primer elemento. Por eso al pasarlo a una función siempre va por referencia, sin & ni *, y la función puede modificarlo.

Consecuencia: la función no sabe cuántos elementos tiene. Por eso el tamaño se pasa siempre como un parámetro aparte.

6 Cadenas de caracteres
Una cadena es un arreglo de char que termina en '\0'
Para guardar N caracteres útiles hay que declarar char cad[N+1]. El lugar extra es para el terminador, y no es opcional: es lo que le dice a printf, strlen y todas las funciones de string.h dónde termina.
Declarar sin lugar para el terminador
char cad[4] = "hola" no deja espacio para el '\0'. En ejecución, printf("%s", cad) y strlen(cad) siguen leyendo memoria más allá del arreglo hasta encontrar un byte cero: imprime basura pegada al texto y devuelve una longitud enorme.

Olvidar sacar el '\n' que deja fgets
Si el usuario escribe Juan y ENTER, la cadena queda "Juan\n": strlen devuelve 5 y strcmp(nombre, "Juan") da distinto de 0, así que toda comparación falla siempre. La línea del strcspn va inmediatamente después del fgets.
Mezclar scanf con fgets sin limpiar el buffer
scanf("%d", &edad) deja el '\n' pendiente; el fgets siguiente lo lee de inmediato, devuelve una cadena vacía y el programa pasa de largo la carga del nombre sin esperar al usuario.

Leer strcmp al revés · el error más frecuente de la unidad
if (strcmp(a, b)) entra al if cuando las cadenas son DISTINTAS, porque strcmp devuelve 0 justo cuando son iguales — y 0 es falso.

La lógica queda invertida sin ningún aviso del compilador. Escribí siempre la comparación explícita: if (strcmp(a, b) == 0).
strcat sobre un destino chico
char dest[10] = "Hola mundo" ya está lleno; strcat(dest, " C") escribe más allá del arreglo. No hay control de tamaño en ejecución: se corrompe la memoria vecina y el programa falla más adelante, en un lugar que no tiene nada que ver.

7 Structs

Un struct agrupa datos de tipos distintos bajo un mismo nombre. Es lo que permite tratar "un alumno" como una sola cosa en lugar de tres arreglos paralelos.

/* Definición con typedef: la forma que usa la cátedra */
typedef struct {
    char nombre[31];
    int padron;
    float promedio;
} t_alumno;

int main()
{
    t_alumno alumno;                    /* una variable del tipo */
    t_alumno curso[MAX_ALUMNOS];        /* un arreglo de structs */

    alumno.padron = 105432;             /* acceso con punto */
    strcpy(alumno.nombre, "Ariel");     /* la cadena se copia, no se asigna */

    curso[0].promedio = 8.5;            /* primero el índice, después el campo */
    return 0;
}
Las dos formas de acceder a un campo
variable.campo — cuando tenés la variable.
puntero->campo — cuando tenés un puntero al struct. Es la forma corta de (*puntero).campo.

Si te aparece un error raro con paréntesis y asteriscos, casi siempre es que corresponde -> y escribiste ., o al revés.
Asignar una cadena de un struct con =
alumno.nombre = "Ariel" no compila: el campo es un arreglo. Va strcpy(alumno.nombre, "Ariel").

En cambio, el struct completo sí se asigna con =: a2 = a1 copia todos los campos, incluidas las cadenas. Es la excepción que confunde.
Structs por valor: se copia todo
Pasar un struct grande por valor a una función copia cada byte, y los cambios adentro no se ven afuera. Si la función tiene que modificarlo —o si el struct es grande— pasalo por referencia: void cargar(t_alumno *a), y adentro a->padron = ....

Conviene para.csv, logs, listados editables a manoMuchos registros iguales, velocidad, acceso por posición

El patrón correcto de lectura hasta fin de archivo

FILE *arch;
t_producto reg;

arch = fopen("productos.dat", "rb");
if (arch == NULL) {                       /* SIEMPRE verificar */
    printf("ERROR: no se pudo abrir el archivo.\n");
    return 1;
}

while (fread(&reg, sizeof(t_producto), 1, arch) == 1) {   /* la condición ES la lectura */
    printf("%d - %s\n", reg.codigo, reg.descripcion);
}

fclose(arch);
El bug clásico: while (!feof(arch)) procesa un registro de más
feof() no predice el fin de archivo: se enciende después de que una lectura ya falló. Con el molde

while (!feof(arch)) { fread(...); procesar(reg); }

la última vuelta lee nada (la lectura falla), pero igual procesa reg, que todavía tiene el registro anterior. Resultado: el último registro aparece duplicado.

La solución es poner la lectura en la condición, como en el código de arriba: while (fread(...) == 1). El mismo razonamiento vale para texto: while (fgets(linea, TAM, arch) != NULL) y while (fscanf(arch, "%d", &n) == 1).
No verificar que fopen haya funcionado
Si el archivo no existe, fopen devuelve NULL y la primera operación sobre ese puntero es una violación de segmento. El if (arch == NULL) es obligatorio, siempre.
Olvidar fclose
Lo escrito queda en un buffer intermedio y puede no llegar nunca al disco si el programa termina sin cerrar. Es un bug que sólo aparece a veces, que es lo peor que puede pasarte.

Posicionamiento (acceso directo)

fseek(arch, n * sizeof(t_producto), SEEK_SET);  /* ir al registro n (0-based) */
ftell(arch);                                     /* posición actual en bytes */
rewind(arch);                                    /* volver al principio */

Esto sólo es práctico en archivos binarios, porque todos los registros miden lo mismo: la posición del registro n se calcula con una multiplicación. En un archivo de texto los renglones tienen largo variable y no hay forma de saltar directo.

El asterisco significa dos cosas distintas
En la declaración (int *p;) el * dice "esto es un puntero".
En el uso (*p = 8;) el * dice "andá a la dirección y escribí ahí".

Es la misma tecla con dos significados, y confundirlos es la fuente número uno de errores de esta unidad.

Dónde vive cada cosa

El stack crece hacia abajo y el heap hacia arriba. Que el heap lo gestione el programador es exactamente por qué hay que llamar a free.

Las cuatro funciones

int *vec;
int n = 10;

vec = (int *) malloc(n * sizeof(int));
if (vec == NULL) {                       /* SIEMPRE verificar */
    printf("ERROR: sin memoria.\n");
    return 1;
}

for (i = 0; i < n; i++) {
    vec[i] = 0;                          /* se usa igual que un arreglo común */
}

free(vec);                               /* devolver la memoria */
vec = NULL;                              /* evita el uso después de liberar */
Perder el puntero original al hacer realloc
v = realloc(v, n); parece inocente, pero si realloc falla devuelve NULL y ya perdiste la dirección del bloque viejo: fuga de memoria garantizada y datos irrecuperables.

Lo correcto es usar un puntero auxiliar: aux = realloc(v, n); if (aux != NULL) v = aux;
Usar la memoria después de free
Liberar no borra el contenido ni pone el puntero en NULL: queda un dangling pointer que sigue apuntando a memoria que ya no es tuya. Escribir ahí corrompe el heap y el programa falla mucho después, en otro lado. Por eso el vec = NULL; del ejemplo.
Fugas: pedir y no liberar
Cada malloc necesita su free. En un programa chico no se nota; en un ciclo, el consumo crece hasta agotar la memoria. Valgrind es la herramienta que la cátedra enseña para detectarlas.
No verificar que malloc devolvió memoria
Si devuelve NULL y no lo chequeás, el primer vec[0] = ... es una escritura en la dirección nula: violación de segmento inmediata.

Matriz dinámica · doble puntero

int **mat;
int i;

mat = (int **) malloc(filas * sizeof(int *));      /* vector de punteros a fila */
for (i = 0; i < filas; i++) {
    mat[i] = (int *) malloc(cols * sizeof(int));   /* cada fila, por separado */
}

/* se usa como una matriz común: mat[i][j] */

for (i = 0; i < filas; i++) {
    free(mat[i]);         /* primero cada fila... */
}
free(mat);                /* ...y recién después el vector de punteros */
El orden de liberación es al revés del de reserva
Si liberás mat primero, perdés las direcciones de las filas y ya no las podés liberar: fuga garantizada. Se reserva de afuera hacia adentro y se libera de adentro hacia afuera.

10 Recursividad
Toda función recursiva tiene exactamente dos partes
Caso base — la condición que corta, sin volver a llamarse. Va primero.
Caso recursivo — se llama a sí misma con un argumento más chico, que se acerca al caso base.

Si falta el caso base, o si el argumento no se achica, la pila de llamadas crece hasta reventar: stack overflow. 
long factorial(int n)
{
    if (n <= 1) {           /* CASO BASE */
        return 1;
    }
    return n * factorial(n - 1);      /* CASO RECURSIVO: n-1 se acerca a 1 */
}
/* Fibonacci: dos llamadas por nivel, y por eso es exponencial */
int fibonacci(int n)
{
    if (n == 0) {
        return 0;
    }
    if (n == 1) {
        return 1;
    }
    return fibonacci(n - 1) + fibonacci(n - 2);
}

La pila de llamadas

Cada llamada apila un juego nuevo de variables locales y parámetros en el stack. Nada se resuelve hasta llegar al caso base: recién ahí se empieza a desapilar y a devolver valores hacia arriba. Por eso factorial(5) no calcula nada hasta llegar a factorial(1).

Caso base que no atrapa todos los casos
if (n == 0) como único caso base falla con negativos: n se aleja del cero para siempre. Usar if (n <= 0) o validar la entrada antes de llamar.

Ojo con el razonamiento inverso: si el caso base es if (n < 10), todo negativo lo cumple y la función devuelve el negativo de una — no hay recursión infinita, pero el resultado no tiene sentido. Validar sigue siendo la solución.
Recursión que no reduce
El argumento de la llamada recursiva tiene que estar estrictamente más cerca del caso base. f(n) llamando a f(n), o a f(n / 1), no reduce nada.
Fibonacci recursivo es exponencial
Cada llamada dispara dos más: fibonacci(40) hace cientos de millones de llamadas y tarda una eternidad. Recursivo se escribe en tres líneas y es elegante, pero para valores grandes la versión iterativa es la única viable. Es un buen ejemplo de que "más corto" no es "mejor".

Los tres métodos de ordenamiento

MétodoIdeaMejor casoIntercambiosCosto
BurbujeoCompara adyacentes en pasadas sucesivasn(n−1)/2 — no se entera de que ya está ordenadoHasta n(n−1)/2O(n²)
Burbujeo optimizadoCorta si una pasada no tuvo intercambiosn−1 (vector ya ordenado)Hasta n(n−1)/2O(n²), mejor caso O(n)
SelecciónBusca el mínimo del tramo y lo lleva al frenten(n−1)/2 — siempre las mismasExactamente n−1O(n²)
InserciónInserta cada elemento entre los ya ordenadosn−1 (vector ya ordenado)Hasta n(n−1)/2 desplazamientosO(n²)
Cuál elegir, según lo que te pregunten
Menos intercambios → selección (exactamente n−1, sin importar los datos). Sirve cuando mover un elemento es caro.
Vector casi ordenado → inserción o burbujeo optimizado: los dos bajan a O(n) en ese caso.
Burbujeo sin optimizar es el peor de los tres: hace todas las pasadas aunque el vector ya esté ordenado.

Búsqueda lineal vs. binaria

Lineal (secuencial)Binaria (dicotómica)
RequisitoNingunoEl vector tiene que estar ORDENADO
IdeaRecorre desde el principioCompara con el medio y descarta la mitad
Peor cason comparacioneslog₂(n) comparaciones
Con n = 1.000.000Hasta 1.000.000~20
int busqueda_binaria(int vec[], int n, int buscado)
{
    int izq = 0, der = n - 1, medio;

    while (izq <= der) {
        medio = (izq + der) / 2;
        if (vec[medio] == buscado) {
            return medio;               /* encontrado: devuelve la posición */
        }
        if (vec[medio] < buscado) {
            izq = medio + 1;            /* descarta la mitad izquierda */
        } else {
            der = medio - 1;            /* descarta la mitad derecha */
        }
    }
    return -1;                          /* no está */
}
Búsqueda binaria sobre un vector desordenado
No da error: da un resultado incorrecto, y encima a veces acierta por casualidad, que es lo que lo vuelve difícil de detectar. El requisito de estar ordenado no es una recomendación.
Los ±1 de la binaria
izq = medio + 1 y der = medio − 1: si escribís izq = medio el ciclo nunca termina cuando quedan dos elementos. Y la condición es izq <= der, no <: con < te perdés el caso de un solo elemento.
