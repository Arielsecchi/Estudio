Compilar y ejecutar a mano

Es lo que hay que saber hacer aunque uses IDE, porque cuando el IDE falla el que te dice qué pasó es el compilador. El comando que da la cátedra:

gcc -g <nombre_archivo>.c -o <nombre_ejecutable>.exe
  • -g · opcional, agrega la información de debug que necesita el depurador. Ponelo siempre mientras desarrollás.
  • -o · indica el nombre del ejecutable de salida. Si lo omitís, gcc genera a.exe (o a.out en Linux) y vas a tener todos tus programas pisándose con el mismo nombre.

Después ejecutás escribiendo el nombre del ejecutable. El primer programa entero, compilado y corrido:

La convención de código de la cátedra

Acá empieza la parte que evita perder puntos gratis. La cátedra publica un documento llamado "Estilo de codificación en C (C Coding Style)", versión 1.1 de 2025, y no es una sugerencia: es la convención adoptada para el curso. Que tu programa funcione y que tu programa esté bien escrito son dos notas distintas.

La cátedra lo funda así: dice que existen varias convenciones —Linux kernel coding style, Kernighan & Ritchie, GNU coding standard— y que para este curso adopta las características principales del Linux kernel coding style, que a su vez es una variante de la de K&R, los autores de The C Programming Language. Los cinco propósitos que declara: organizar el código de forma clara, que sea fácil de leer para otros, fácil de comprender, fácil de mantener, y simplificar la detección de errores.

Regla 2 · Ubicación de las llaves: hay dos reglas distintas y se confunden

La regla que todo el mundo se lleva mal
Las funciones son el caso especial. En una función, la llave de apertura va en la primera columna, o sea en su propia línea, pegada al margen. En todos los demás casos —if, else, for, while, do, switch— la llave va al final del renglón.

Es exactamente el estilo del kernel de Linux, y el motivo histórico es que una función es la única construcción de C que no se anida dentro de otra.

Regla 3 · Cuándo se omiten las llaves

La cátedra escribe: "Es conveniente omitir las llaves si una sola sentencia será ejecutada", y da los dos ejemplos:

if (condicion)
        accion();

if (condicion)
        incrementar();
else
        decrementar();

Y después la regla que sigue, que es la que se olvida:

Si una rama del if lleva llaves, las llevan las dos
Textual de la cátedra: "En el caso que una de las ramas del if ejecute más de una sentencia, se utilizan llaves en ambas ramas." O sea, esto está bien aunque el else tenga una sola línea: 
if (condicion) {
        incrementar();
        accion();
} else {
        decrementar();
}
Y no está bien poner llaves sólo arriba y dejar el else pelado.

Regla 6 · Indentación, comentarios y el resto del estilo

Esto no está en el documento de convención sino en la clase introductoria de Bianchi, y es igual de normativo porque es lo que muestran los ejemplos:

  • Indentar con una tabulación de 4 espacios. Textual: "indentar el código para una mejor legibilidad, utilizando una tabulación de 4 espacios". Los fragmentos de la guía de estilo están copiados del kernel de Linux y se ven con sangría más ancha; el número que la cátedra escribe con todas las letras es 4. Usá 4 y, sobre todo, usá siempre el mismo en todo el archivo.
  • Un bloque de código va encerrado entre { }; las instrucciones terminan con ;.
  • Comentario de varias líneas: se abre con /* y se cierra con */. De una línea o a continuación del código: //.
  • Usar minúsculas para las instrucciones.

La convención es de estilo, no de semántica: el propio ejemplo de la cátedra tiene un bug
El switch que la guía de estilo usa para mostrar dónde van las llaves no tiene ningún break. Lo compilamos tal cual, con valor = 1: 
int var;
int valor = 1;

switch (valor) {
case 1:
        var = 5;
case 2:
        var = 10;
default:
        var = 100;
}
printf("var = %d\n", var);
sin break, valor = 1  ->  var = 100
con break, valor = 1  ->  var = 5
Con valor = 1 entra por case 1, asigna 5, y sigue cayendo por case 2 y por default: termina en 100. Ese ejemplo enseña indentación, no comportamiento del switch. El break lo ponés vos, y la clase de switch de Bianchi lo dice aparte: "el uso del break se hace necesario, para salir del switch y evitar que se ejecuten las acciones que estén en los case que están por debajo del case que hizo verdadera la evaluación".

La checklist de 60 segundos antes de entregar

Pasala línea por línea sobre tu código. Cada punto es una regla escrita de la cátedra:

  1. ¿Todas las variables y funciones en snake_case, sin mayúsculas ni camelCase?
  2. ¿Todos los nombres describen lo que guardan? (salvo i, j de índice)
  3. ¿La llave de apertura de cada función está en su propia línea, en la primera columna?
  4. ¿La llave de todo el resto (if, for, while, do, switch) está al final del renglón?
  5. ¿Hay espacio después de if, switch, case, for, do, while?
  6. ¿Hay espacio a cada lado de =, +, -, <, >, *, /, %, ||, &&, ^, <=, >=, ==, !=?
  7. ¿Ningún espacio en a++, ++a, a--, --a?

scanf: tres trampas y todas se cobran

La forma es scanf("%d", &variable); y el & no es decorativo: printf recibe el valor, scanf necesita la dirección donde escribir.

Trampa 1 · scanf sin el &: compila y revienta al ejecutar
Compilamos scanf("%d", edad); y esto fue lo que pasó, textual: 
warning C4477: 'scanf' : la cadena de formato '%d' requiere un argumento de tipo 'int *',
                pero el argumento variadico 1 tiene el tipo 'int'
warning C4700: se utilizo la variable local 'edad' sin inicializar
Dos warnings, cero errores: el ejecutable se generó. Al correrlo, el programa murió con código de salida 0xC0000409. Sin el &, scanf toma el contenido basura de edad y lo usa como si fuera una dirección de memoria, y escribe ahí.

El & va siempre en variables simples. La única excepción son las cadenas: scanf("%s", nombre) va sin &, porque el nombre de un arreglo ya es la dirección.
Trampa 2 · el %c que se come el Enter
Lo compilamos con las dos versiones y estas son las dos salidas reales, con la misma entrada (25.5 y C): 
scanf("%c", &unidad);   ->  unidad = [
] (codigo ASCII 10)

scanf(" %c", &unidad);  ->  unidad = [C] (codigo ASCII 67)
El scanf("%f", ...) anterior lee el número y deja el Enter en el buffer. El %c siguiente levanta ese Enter, que es el carácter ASCII 10, y el programa "no espera" al usuario. La solución es un espacio antes del especificador: " %c". Ese espacio le dice a scanf que descarte los blancos pendientes.
Trampa 3 · float es %f pero double es obligatoriamente %lf
En printf los dos andan con %f, porque el float se promueve a double al pasarlo. En scanf no: ahí se pasa una dirección y el tipo tiene que coincidir exacto. scanf("%f", &un_double) escribe 4 bytes sobre una variable de 8 y deja el valor absurdo, sin error.

Pre y post incremento, con el programa que lo demuestra

La diferencia es cuándo se usa el valor, no cuánto vale al final. En los dos casos la variable termina incrementada en uno.

int a = 5;

printf("%d ", a++);      /* usa 5, despues incrementa */
printf("%d ", a);        /* imprime a tal cual */
printf("%d\n", ++a);     /* incrementa primero, usa 7 */
printf("a al final = %d\n", a);

a = 5;
int b = a++;
printf("b = a++  ->  b = %d, a = %d\n", b, a);

a = 5;
b = ++a;
printf("b = ++a  ->  b = %d, a = %d\n", b, a);
Salida real
5 6 7
a al final = 7
b = a++  ->  b = 5, a = 6
b = ++a  ->  b = 6, a = 6
Leelo en las dos últimas líneas, que son las que aclaran todo: con post-incremento b = a++ la variable b se queda con el valor viejo (5) y a avanza a 6. Con pre-incremento b = ++a, a avanza primero y b se queda con el valor nuevo (6). En los dos casos a termina en 6: lo que cambia es qué se llevó b.
Nunca pongas dos incrementos de la misma variable en una sola instrucción
Las tres llamadas de arriba son tres printf separados, y eso es lo que hace que el resultado sea predecible: cada instrucción termina antes de que empiece la siguiente. En cambio printf("%d %d", a++, ++a); es comportamiento indefinido en C: el estándar no dice en qué orden se evalúan los argumentos, y el resultado puede cambiar entre compiladores, entre versiones del mismo compilador y hasta con el nivel de optimización.

No hay respuesta correcta a "¿qué imprime printf("%d %d", a++, ++a)?". Si te lo cruzás, la respuesta es "depende del compilador, no está definido". Y en tu código: un solo efecto por instrucción.

Y acordate del estilo: la convención pide a++, ++a sin ningún espacio.

switch: cuándo conviene sobre el if anidado

La cátedra lo justifica textual: "cuando las alternativas de decisión son múltiples, en lugar de anidar if, puede ser conveniente utilizar el condicional switch, ya que permitirá reflejar de forma más clara los distintos flujos del programa".

unsigned short mes;

printf("Ingrese el nro. del mes: ");
scanf("%hu", &mes);
printf("\nEl mes ingresado por Ud. es: ");
switch (mes) {
case 1:
    printf("Enero");
    break;
case 2:
    printf("Febrero");
    break;
default:
    printf("Inexistente");
}
Salidas reales, con dos entradas
mes = 2   ->  El mes ingresado por Ud. es: Febrero
mes = 13  ->  El mes ingresado por Ud. es: Inexistente
  • La expresión del switch tiene que ser entera (o char, que es un entero). No se puede switchear sobre un float ni sobre una cadena.
  • Cada case compara contra una constante, no contra un rango ni contra una variable.
  • El break es obligatorio en la práctica. Sin él, la ejecución cae en cascada a los case de abajo hasta encontrar un break o el final. La cátedra: "el uso del break se hace necesario, para salir del switch y evitar que se ejecuten las acciones que estén en los case que están por debajo del case que hizo verdadera la evaluación".
  • default es opcional ("la rama default puede no utilizarse") y no tiene por qué ir al final, aunque siempre se escribe último.
  • Dos case pegados sin nada en el medio comparten cuerpo: es la única caída en cascada que se usa a propósito.

Por qué validar entrada va con do..while y no con while
Con while (num < 1 || num > 20) { scanf(...); } y num sin leer todavía, la condición se evalúa contra basura: si esa basura cae dentro del rango, el ciclo no se ejecuta nunca y el programa sigue con un valor inventado. El do..while pide el dato primero y evalúa después, que es exactamente el orden que hace falta.

El ejemplo de la cátedra: 
do {
    printf("Ingrese numero entre 1 y 20: ");
    scanf("%d", &num);
} while ((num < 1) || (num > 20));
Los dos ciclos que no hacen lo que parecen
1 · El ; de más. Salida real de for (i = 0; i < 5; i++); seguido de un printf("%d ", i);:

El ciclo dio sus cinco vueltas sin hacer nada y el printf, que quedó afuera, corrió una sola vez con i ya en 5.

2 · La asignación en la condición. while (num = 1) con num arrancando en 3: le pusimos un corte de seguridad a las 5 vueltas para poder compilarlo, y dio 5 vueltas. La versión correcta, while (num == 1), dio 0 vueltas —porque 3 no es 1—. La asignación devuelve 1, que es verdadero, y encima pisa la variable de control en cada evaluación: ciclo infinito. == compara, = asigna.

Las diez trampas de esta sección, en una lista

  1. División entera disfrazada de promedio. (7 + 8) / 2 da 7, no 7.5, aunque lo guardes en un float. Casteá antes de dividir.

  3. = en vez de == en una condición. if (num = 1) entra siempre; while (num = 1) es infinito.
  4. ; de más después de if, for o while. El bloque de abajo se ejecuta suelto.
  5. switch sin break. Cae en cascada y queda el último valor asignado.
  6. else colgado. Se pega al if más cercano sin else, no al que sugiere la indentación.

  8. Variable sin inicializar. Un acumulador arranca con basura, no con cero.
  9. #define escrito como asignación. #define MAX = 50; rompe en la línea donde se usa la constante.

La asimetría entre printf y scanf con los reales
En printf, %f sirve para float y para double, porque el float se promueve a double al pasarlo. En scanf no: ahí va %f para float y %lf para double, sí o sí. Si leés un double con %f, scanf escribe 4 bytes en una variable de 8 y la mitad de la variable queda con basura.

scanf · el & y el Enter que se queda en el buffer

Dos reglas y se acabó el tema:

  1. Todas las variables simples llevan &: scanf("%d", &edad). Sin el & le pasás el contenido de una variable sin inicializar y scanf escribe en una dirección de memoria inventada.
  2. Si vas a leer un char después de haber leído un número, el %c lleva un espacio adelante: scanf(" %c", &unidad).

Por qué: cuando el usuario escribe 24.5 y aprieta Enter, el %f consume 24.5 y deja el Enter en el buffer. El scanf("%c", ...) siguiente toma el primer carácter disponible, que es ese salto de línea, y ni siquiera frena a pedir nada: el programa pasa de largo. El espacio adelante del %c le dice a scanf «salteá todos los blancos antes de leer». Con %d, %f y %s no hace falta porque ya saltean espacios solos.

a++ y ++a · qué valor entrega la expresión

Como sentencia suelta son idénticos: los dos incrementan. La diferencia aparece solo cuando el resultado se usa en la misma expresión.

int a = 5;
int b;

b = a++;
printf("%d %d", a, b);
Salida real
6 5
El post-incremento entrega a la expresión el valor viejo de a (5), que es el que se guarda en b, y recién después incrementa a, que queda en 6. Con b = ++a; (pre-incremento) primero incrementa y después entrega el valor nuevo: las dos variables quedan en 6 y la salida sería 6 6.

Regla de supervivencia: si el resultado del incremento se usa en la misma línea, escribilo aparte. Primero la operación, después el ++. Y acordate de la convención de la cátedra: sin espacios — a++, no a ++.

Máximo y mínimo · por qué no se inicializan en 0

Es el error más frecuente de toda la guía y no salta a la vista porque el programa responde, solo que responde un valor que el usuario nunca ingresó.

Verificado: qué pasa con menor = 0
int num, menor = 0;

printf("Numero: ");
scanf("%d", &num);
while (num != 0) {
    if (num < menor)
        menor = num;
    printf("Numero: ");
    scanf("%d", &num);
}
printf("Menor: %d", menor);
Con la serie 5, 8, 3, 0 este programa informa Menor: 0. Ningún valor ingresado es menor que 0, el if nunca se cumple y menor conserva la inicialización. Debería informar 3.

La solución no es inventar un valor grande: es tomar el primer dato real de la serie, detectándolo con el contador.

if (cantidad == 0) {
    mayor = num;
    menor = num;
} else if (num > mayor) {
    mayor = num;
} else if (num < menor) {
    menor = num;
}

La única excepción es cuando el dominio está acotado por definición. En el ejercicio 16b los valores posibles son los dígitos 0 a 9, así que menor = 9 y mayor = 0 son inicializaciones seguras: cualquier dígito real las empuja o las empata.

resto = num;                  /* copia: el ciclo destruye la variable */

Trampas de esta guía

Usar = donde va ==
if (x = 0) no compara: asigna 0 a x y evalúa el resultado de la asignación, que es 0, o sea falso. Compilado y ejecutado con x = 3, imprime distinto de cero — y de paso te pisó el 3. Compila sin error, a lo sumo con un warning. Costumbre que salva: leelo en voz alta. «Si x vale cero» es ==; «x pasa a valer cero» es =.
Punto y coma después del if, del for o del while
for (i = 0; i < 5; i++); es un ciclo con cuerpo vacío que gira 5 veces sin hacer nada; lo que escribiste indentado debajo se ejecuta una sola vez, ya fuera del ciclo. Verificado: ese fragmento imprime 5, no 0 1 2 3 4. Con while es peor: cuerpo vacío = ciclo infinito y el programa se cuelga. La línea que abre un if/for/while nunca termina en ;.
Dos sentencias colgando de un if sin llaves
En if (nota >= 4) printf("Aprobado"); printf("Felicitaciones"); la segunda línea no pertenece al if y se ejecuta siempre, por más prolija que esté la indentación: C no mira los espacios. Verificado con nota = 2: imprime Felicitaciones Fin. La convención de la cátedra permite omitir las llaves solo con una sentencia; en cuanto hay dos, van llaves en todas las ramas.
No actualizar la variable de control adentro del while
Si falta el scanf del final del cuerpo, o falta el resto = resto / 10;, la condición nunca cambia y el ciclo es infinito. Antes de dar por cerrado un while, buscá con el dedo la línea que modifica la variable de la condición. Si no la encontrás, el ciclo no termina.
Contar el centinela como un dato más
Si acumulás antes de evaluar la condición de corte, el 0 final entra en la cuenta y el promedio sale dividido por uno de más. Lo evita la lectura anticipada. Y siempre preguntá if (cantidad == 0) antes de dividir: si el usuario corta de entrada, la división por cero te tira el programa abajo. Verificado: con el molde correcto y entrada 0 directo, el programa contesta No se ingresaron numeros.
Destruir el número original
En el ejercicio 16 el ciclo consume la variable hasta dejarla en 0. Si iterás sobre num en vez de sobre una copia, el mensaje final dice «El numero 0 tiene…». Copiá siempre: resto = num;.
Confundir «dígitos pares» con «el número es par»
Específico del 16a. Hay que evaluar digito % 2, no num % 2. El número 4071 tiene 2 dígitos pares (el 4 y el 0) y 2 impares (el 7 y el 1), y sin embargo el número entero es impar.

«Para la solución de los siguientes ejercicios, no debes imprimir resultados dentro de las funciones que escribas. Los resultados deben ser devueltos mediante el return de la función.»

Y dos renglones más abajo: «Luego de escribir cada función, probala, invocándola desde el bloque principal del programa, pasándole distintos valores para que la prueba contemple varias alternativas y así estar seguro que funciona adecuadamente.»

Las dos frases son consigna, no consejo. La primera define dónde va cada cosa: la función calcula, el main muestra. La segunda define qué se entrega: no alcanza con la función, hace falta un main que la llame con al menos un caso típico, un caso borde y un caso grande.

Qué pasa de verdad si te olvidás el prototipo
No es lo que dice el mito. Se compiló a propósito un programa que llama a cuadrado(5) sin haberla declarado, con la definición debajo del main. MSVC contesta:

Parámetros por valor · la función recibe una copia

Este es el concepto que más se pregunta y el que más gente da por sabido sin entenderlo. En C, todo parámetro se pasa por valor: la función recibe una copia del dato, y lo que le haga a esa copia muere cuando la función termina.

Verificado: por valor no modifica nada
void duplicar(int n);

int main()
{
    int valor = 5;

    duplicar(valor);
    printf("%d", valor);

    return 0;
}

void duplicar(int n)
{
    n = n * 2;
}
Salida real: 5. La función duplicó su propia copia, no la variable del main. Que el parámetro se llame igual que la variable del llamador tampoco cambiaría nada: son dos casilleros de memoria distintos.

Parámetros por referencia · la única forma de devolver dos cosas

Cuando el enunciado dice «devuelva por parámetros» o «la convierta en los parámetros numéricos aaaa, mm y dd», te está pidiendo punteros. Es el caso de los ejercicios 9 y 10 de Funciones: un return devuelve un valor y ahí hacen falta tres o cuatro.

Verificado: por referencia sí modifica
void duplicar(int *n);

int main()
{
    int valor = 5;

    duplicar(&valor);
    printf("%d", valor);

    return 0;
}

void duplicar(int *n)
{
    *n = *n * 2;
}
Salida real: 10. La función no recibió el valor 5 sino la dirección de valor, y el *n escribe en esa dirección.

Contá los * del prototipo y los & de la llamada: tienen que ser la misma cantidad y en el mismo orden. Después verificá que cada parámetro de salida se escriba al menos una vez con * adentro de la función. Si alguno no aparece, el main va a imprimir basura.

Verificado: la local tapa a la global (shadowing)
int contador = 1;          /* GLOBAL */

{
    int contador = 10;     /* LOCAL: tapa a la global dentro de main */

    sumar();
    printf("%d", contador);

    return 0;

{
    contador = contador + 5;   /* toca la GLOBAL, que pasa de 1 a 6 */

Salida real: 10. La función modificó la global, pero el printf del main lee la local, que la tapa. La global quedó en 6 y nadie se enteró.
Por qué la cátedra no quiere globales
No es purismo: es que el ejemplo de arriba es imposible de depurar. Un programa modular bien escrito no necesita ninguna variable global. Los acumuladores viven en el main y se pasan por puntero, o la función devuelve su aporte y el main acumula. Si te ves tentado de poner una global para "compartir" un contador entre dos funciones, lo que te falta es un parámetro.

Cómo se decide cuántas funciones tiene un programa

Esta es la única habilidad que evalúa la guía de Programación Modular, y hay un método:

  1. Leé el enunciado y subrayá los sustantivos de acción: "contar múltiplos", "calcular el factorial", "verificar si es primo", "informar el nombre del mes". Cada uno es una función.
  2. Responsabilidad única: cada función hace una cosa y su nombre lo dice completo. Si el nombre necesita una "y" (validar_y_mostrar), son dos funciones.
  3. El main solo pide datos, valida, llama y muestra. No calcula.
  4. La validación de lo que ingresa el usuario va en el main, nunca adentro de la función de cálculo: la función tiene que poder llamarse desde cualquier lado.
  5. Reutilizá. Si ya escribiste es_primo, los ejercicios 5, 6 y 12 de la guía modular no la vuelven a implementar: la llaman.
El test que dice si está bien modularizado
Tapá el cuerpo del main y leé solo la secuencia de llamadas. Si esa lista de nombres se lee como el enunciado en castellano, el programa está bien repartido. En el ejercicio modular 4 la secuencia es descomponer_fecha ▸ fecha_valida ▸ nombre_del_mes, que es literalmente lo que pide la consigna: descomponer, verificar e informar.

El flujo del programa cuando está modularizado

Un programa con funciones no se ejecuta de arriba hacia abajo. El orden en el archivo no es el orden de ejecución:

  1. Siempre arranca en main, esté donde esté en el archivo.
  2. Al llegar a una llamada, la ejecución se va a la función: se crean sus variables locales, los parámetros se llenan con una copia de los argumentos.
  3. Cuando la función hace return —o termina, si es void— sus variables locales dejan de existir y la ejecución vuelve a la línea exacta desde donde se la llamó, con el valor devuelto en la mano.
  4. Ese valor se usa donde estaba la llamada. Por eso y = cuadrado(x) + cuadrado(x + 1); es una sola línea con dos idas y vueltas.
Verificado
int cuadrado(int n)
{
    return n * n;
}

int main()
{
    int x = 3;
    int y;

    y = cuadrado(x) + cuadrado(x + 1);
    printf("%d", y);

    return 0;
}
Salida real: 25 — o sea 9 + 16. La función se ejecutó dos veces, con 3 y con 4, y x quedó en 3 las dos veces porque se pasó por valor.

Un detalle del return que se pregunta: termina la función en el acto, esté donde esté. Un return adentro de un for abandona el ciclo y la función de una sola vez. Eso es lo que permite escribir las funciones booleanas con salida temprana: apenas encontrás un divisor, return false y listo, no hace falta seguir buscando ni llevar una bandera.

Qué protege la guarda exactamente
Repetir el mismo prototipo dos veces es perfectamente legal en C y no da ningún error. Lo que sí revienta al duplicarse son los typedef, los struct y los enum: ahí aparece un redefinition of 'struct fecha'. La guarda se pone siempre igual, porque el día que agregues un typedef al header no te vas a acordar de ponerla.

Se le pasan al compilador todos los .c. Al .h no se lo compila nunca:

Códigos de error por retorno

Dos ejercicios de la guía de Funciones lo piden explícitamente: el 3 («Si no se puede calcular el factorial del valor recibido, la función deberá devolver 0») y el 11 («En el caso que los parámetros no sean consistentes y la extracción no puede realizarse la función debe retornar -1»). La regla para elegir el valor:

El código de error tiene que ser un valor que la función nunca podría devolver legítimamente
En el ejercicio 3 el 0 funciona perfecto: ningún factorial vale 0, así que no hay ambigüedad posible. En el 11 el -1 también, porque un sub-código es siempre no negativo. Pero ojo con generalizarlo: si tu función potencia devolviera 0 como código de error, no habría forma de distinguirlo del legítimo 0³ = 0. Cuando el dominio del resultado ocupa todos los valores del tipo, ya no hay lugar para un código de error y hay que cambiar la firma: bool potencia(int a, int b, double *resultado); — devuelve si pudo, y el valor sale por puntero.

Trampas de estas dos guías

Imprimir adentro de la función
Está prohibido por el encabezado de la guía. Y el motivo es práctico: una función que imprime sirve una sola vez. Si es_primo imprimiera "es primo", no la podrías reutilizar en el ejercicio 12 modular, que necesita el resultado para decidir qué calcular, no para mostrarlo.
Devolver un tipo y declararlo con otro
Escribir int factorial(int n) y adentro acumular en un unsigned long long: el return trunca a int y se pierde todo. El tipo de retorno del prototipo, el de la definición y el de la variable acumuladora tienen que ser el mismo.
El printf con el especificador equivocado
Una función que devuelve long long impresa con %d muestra cualquier cosa. Va %lld; para unsigned long long va %llu. Es el error que hace que suma_n(120120) "no funcione" cuando la función está perfecta.
Validar adentro de la función de cálculo
Si factorial le pide datos al usuario, ya no es una función de cálculo: es medio programa. La validación va en el main o en una función leer_... dedicada. Lo único que sí va adentro es rechazar un parámetro inconsistente devolviendo un código de error, que es otra cosa.

Qué es un arreglo, con las palabras de la cátedra

La clase de Bianchi lo define en cinco viñetas, y conviene tomarlas literalmente porque cada una tiene una consecuencia en el código:

La consecuencia de "estructura estática" que se cobra en el parcial
El tamaño va en una constante, no en una variable. #define MAX 100 y después int v[MAX];. Si escribís int v[n]; con n leída del teclado estás usando un arreglo de tamaño variable: C99 lo incorporó al estándar y C11 lo volvió opcional, y MSVC no lo implementa (lo verificamos: Visual Studio corta con error C2057: se esperaba una expresión constante). La cátedra nunca lo usa: siempre declara el máximo físico con #define y trabaja con una parte.

Máximo físico y máximo lógico: el par de conceptos que ordena todo

Es la nomenclatura propia de esta cátedra y aparece con esos nombres en la clase, en las guías y en los enunciados ("un vector de tipo vector_t ya cargado y su máximo lógico"). Aprendelos así:

El ML no lo sabe el arreglo: lo sabés vos
En C un arreglo no guarda cuántos elementos válidos tiene. No hay v.length ni nada parecido. El máximo lógico es una variable int aparte que vos actualizás cada vez que cargás o borrás, y que tenés que pasar como parámetro a cada función que reciba el vector. Por eso casi todas las funciones de la guía reciben dos cosas: el vector y su ML.
El primer elemento está en la posición 0
La clase lo repite: "El primer elemento ocupa la posición 0 del arreglo, por lo tanto en un arreglo de N elementos, el último estará en la posición N-1". Primer elemento v[0], último v[n-1], intermedios entre 1 y n-2.

El error que sigue de acá es el más caro de todos y es un desborde: escribir for (i = 1; i <= n; i++) en vez de for (i = 0; i < n; i++). En C nadie te avisa: no hay chequeo de rango. El programa pisa memoria que no es suya y compila igual. A veces "anda", y ese es el peor escenario porque en el parcial vas a jurar que está bien.

Declaración: tipo, nombre y cantidad

La sintaxis de la clase es tipo nombre_arreglo[cantidad_elementos]. Estos son los ejemplos textuales del material:

int   v_nros[100];              /* 100 enteros                     */
float v_reales[100];            /* 100 reales                      */
char  v_chars[25];              /* 25 caracteres                   */
int   v_pares[] = {2,4,6,8,10}; /* declarado por extension: 5      */

int m_enteros[5][4];                        /* 5 filas x 4 columnas */
int m_enteros_2[3][3] = {{1,2,3},{4,5,6}};  /* por extension        */
Qué pasa con lo que no inicializás
Si escribís int v[5] = {1, 2, 3};, las posiciones 3 y 4 quedan en 0: cuando hay lista de inicialización, el resto se completa con ceros. Pero si escribís int v[5]; a secas, adentro de una función, las cinco posiciones tienen basura, no ceros. Los dos casos se ven parecidos en el código y se comportan al revés.

typedef y #define: cómo lo escribe la cátedra

La clase dedica dos diapositivas a esto y las guías lo dan por sabido: los enunciados 8 de Vectores y 4 de Matrices arrancan dándote el typedef y esperan que lo uses. La sintaxis es typedef tipo_dato nombre_del_tipo:

#define MAX 1000

typedef int   vector_t[MAX];        /* un vector de MAX enteros    */
typedef float tv_reales[30];        /* un vector de 30 reales      */
typedef int   tm_enteros[5][7];     /* una matriz de 5 x 7 enteros */

vector_t  v;                        /* ahora declarar es una linea */
tm_enteros m_nros_enteros;

El beneficio que da la clase: "cada vez que hagamos un cambio en la declaración del tipo, el mismo se reflejará automáticamente en todas aquellas variables que se hayan declarado con ese tipo". En la práctica el beneficio grande es otro: la firma de las funciones queda legible. bool analizar(vector_t v, int ml, int *menor_dif) se lee de un vistazo.

Las dos restricciones que la clase marca en rojo

No se pueden asignar ni comparar arreglos directamente
La diapositiva lo dice con un ejemplo tachado: vec_1 = vec_2 NO; hay que hacerlo elemento por elemento con un for.

Lo compilamos para ver el error exacto que te va a tirar Visual Studio: 
int v1[3] = {1, 2, 3};
int v2[3] = {1, 2, 3};

v1 = v2;
d53.c(10): error C2106: '=': el operando izquierdo debe ser valor L
Ese "no es valor L" (lvalue) significa: el nombre de un arreglo no es algo a lo que se le pueda asignar. Es una dirección fija, no una variable.

La comparación es peor, porque sí compila y da un resultado equivocado sin avisar:

int v1[3] = {1, 2, 3};
int v2[3] = {1, 2, 3};

if (v1 == v2)
    printf("v1 == v2 dio VERDADERO\n");
else
    printf("v1 == v2 dio FALSO (compara direcciones, no contenido)\n");
v1 == v2 dio FALSO (compara direcciones, no contenido)
Comparando elemento por elemento: iguales

Los contenidos son idénticos y aun así v1 == v2 da falso: lo que se compara son las direcciones de los dos arreglos, que obviamente son distintas. Para comparar contenido hay que recorrer.

Pasaje de arreglos a funciones, y por qué la cátedra dice "por referencia"

La clase lo enuncia así: "Los parámetros de tipo arreglo serán pasados siempre por referencia, sin necesidad de indicarlo con el símbolo &". Es la regla operativa correcta y es la que te van a tomar. Lo que pasa por abajo es un poco distinto y conviene saberlo porque explica dos cosas que te van a morder.

Cuando escribís void tocar(int v[], int ml), el parámetro no es un arreglo: es un puntero al primer elemento. El nombre del arreglo, al pasarlo, "se degrada" a la dirección de v[0]. Este programa lo muestra medido:

#include <stdio.h>

#define MAX 5

{
    v[0] = 999;
    printf("Adentro de la funcion: sizeof(v) = %d\n", (int)sizeof(v));
    printf("Adentro de la funcion: ml = %d\n", ml);
}

void tocar_copia(int x)
{
    x = 999;

Cómo devolver varios resultados: el patrón de los punteros de salida

El ejercicio 6 de Vectores y el 8 piden devolver dos cosas desde una función. En C una función devuelve un solo valor con return; el resto se devuelve por parámetro, con puntero:

Los paréntesis de (*negativos)++ no son decorativos
*negativos++ significa otra cosa completamente distinta: ++ tiene más precedencia que *, así que incrementa el puntero (lo hace apuntar al siguiente int en memoria) y no el valor apuntado. Compila sin una sola advertencia y arruina el resultado. Escribí siempre (*contador)++, con paréntesis.

Matrices: dos coordenadas, todo lo demás igual

La clase lo plantea como la extensión natural: se accede con matriz[fila][columna], y hay cuatro máximos en juego: MF de filas, ML de filas, MF de columnas, ML de columnas, con 0 <= MLF <= MFF y 0 <= MLC <= MFC. Primer elemento m[0][0], último m[n-1][m-1].

Es el índice que más se equivoca. Con N = 5: i = 0 da m[0][4] (arriba a la derecha) e i = 4 da m[4][0] (abajo a la izquierda). Si escribís m[i][N - i] te salís del arreglo en la primera vuelta; si escribís m[i][N - i - 1] es lo mismo que N - 1 - i y está bien.

Verificación mental rápida: fila + columna tiene que dar siempre N − 1. En la principal, fila = columna.

La definición, textual de la clase

Palabra de la cátedra
"Una cadena de caracteres en C es un tipo particular de vector, que contiene elementos de tipo char, siendo el último el carácter nulo '\0'."

Leelo dos veces, porque las dos mitades tienen consecuencias distintas y las dos se cobran:

  • "es un vector" ⇒ todo lo de la sección 5 sigue valiendo. Se recorre con for, se pasa a funciones por referencia, no se puede asignar con = ni comparar con ==, y el primer carácter está en la posición 0.
  • "el último es '\0'" ⇒ hay un byte más que caracteres, y ese byte no es opcional. Es lo que separa una cadena de un arreglo de char cualquiera.

Por qué char[N + 1] y no char[N]

Si querés guardar hasta N caracteres visibles, necesitás N + 1 bytes: los N del texto más el terminador. Esta convención está en toda la cátedra y hay que escribirla así siempre:

#define LARGO_NOMBRE 30

typedef char t_nombre[LARGO_NOMBRE + 1];   /* 30 caracteres utiles + '\0' */

Medido, para que no quede como una regla arbitraria:

char saludo[15] = "HOLA MUNDO";

printf("saludo[10] es el terminador: %d\n", (int)saludo[10]);

La traducción exacta del vocabulario de la sección anterior
En una cadena, el máximo físico es sizeof (lo que reservaste al declarar) y el máximo lógico es strlen (lo que hay escrito hasta el terminador). Es el mismo par de conceptos de los vectores, con la diferencia enorme de que acá el ML no lo tenés que llevar vos en una variable: está guardado dentro de la propia cadena, en forma de '\0'. Por eso las funciones que reciben cadenas casi nunca piden un parámetro de longitud.
Todo lo malo que pasa con cadenas empieza por un terminador que falta
strlen, strcpy, strcat, strcmp y %s todos recorren hasta encontrar el '\0'. Si no está, siguen leyendo memoria ajena hasta toparse con un cero por casualidad. Resultado: un largo absurdo, caracteres de basura en pantalla o el programa que se cae varias líneas después de la que tiene el error.

Y lo peor: a veces "anda", porque la memoria de al lado tenía un cero. Ese es el bug que aparece recién en la máquina del corrector.

El casteo a (unsigned char) no es paranoia
Las funciones de ctype.h están definidas para valores representables como unsigned char o para EOF. En las plataformas donde char tiene signo —la mayoría— un carácter no ASCII, como una ñ o una vocal acentuada, llega como número negativo y el comportamiento queda indefinido: puede devolver cualquier cosa o caerse.

Escribí siempre isdigit((unsigned char)cadena[i]). Y fijate que el ejercicio 2 de la guía dice literalmente "No tener en cuenta la ñ, ni las vocales acentuadas": la cátedra sabe que ese es un terreno minado.

Mirá la alineación de la columna, no las palabras
El printf usa %-10s, que rellena hasta 10 bytes. Las palabras sin acento quedan alineadas; las acentuadas quedan corridas, porque cada vocal acentuada ocupa dos bytes y printf cuenta bytes, no letras.

La consecuencia real: strlen("café") no devuelve 4. Y cadena[largo - 1] no te da la letra final sino el último byte, que puede ser la mitad de un carácter. Por eso una regla como "si termina en á" no se puede escribir comparando un solo char: hay que comparar el sufijo completo, con strcmp sobre la cola de la palabra.

Para el examen: si el enunciado no menciona acentos, trabajá sólo con ASCII y no te compliques. Si los menciona —como el 9, que tiene reglas específicas para é, á, í, ó, ú— aclarás en un comentario cómo estás representando esos caracteres y comparás por sufijo, nunca por carácter suelto.

Los dos patrones que resuelven la mitad de la guía

Patrón A · La máquina de estados para contar palabras. Sirve para los ejercicios 3 y 14, y para cualquier "cuántas palabras / cuántos grupos hay":

int cantidad = 0;
bool en_palabra = false;

for (i = 0; cadena[i] != '\0'; i++) {
    if (isspace((unsigned char)cadena[i]))
        en_palabra = false;
    else if (!en_palabra) {
        en_palabra = true;
        cantidad++;      /* recien pase de blanco a no-blanco: palabra nueva */
    }
}

La palabra se cuenta en la transición de blanco a no-blanco, no en cada carácter. Eso resuelve solo los blancos repetidos, los del principio y los del final. Contar espacios y sumar uno no funciona: con " Hoy es 30 de Junio de 2021 " hay 13 espacios y la respuesta correcta es 7, no 14.

Patrón B · Los dos índices que se acercan. Sirve para los ejercicios 4, 7 y 8:

int i = 0;
int j = (int)strlen(cadena) - 1;

while (i < j) {
    ... /* comparar o intercambiar cadena[i] con cadena[j] */
    i++;
    j--;
}

Recorre la cadena una sola vez aunque parezca que la mira dos veces: entre los dos índices cubren cada posición exactamente una vez. Por eso cumple con el "a lo sumo una vez" de los enunciados.

Qué te da la cátedra en esta unidad, y qué no

La pestaña Struct del campus es de las más flacas de la materia: cero videos, dos archivos. Uno es el Apunte básico structs en C (Cátedra Azcurra, 2025, v1.0), seis páginas; el otro es la Solución Ejercicio Tabla de Alumnos. Lo que hay que sacar de esta sección
Struct no es un tema difícil: son seis reglas y ninguna es sutil. Lo que sí es difícil es la combinación struct + arreglo + archivo, que es exactamente lo que piden las entregas y lo que arma la Guía Struct. Todo el peso está en dos preguntas que hay que saber contestar sin pensar: ¿esto va por valor o por referencia? y ¿esto es un struct o un arreglo?, porque las dos cosas se comportan al revés.

Definir un struct: la forma que usa la cátedra

La cátedra siempre declara con typedef, nunca con struct nombre { ... }; a secas. El apunte lo escribe así, textual:

typedef struct {
    int legajo;
    char nombre[30];
    char apellido[30];
    bool regular;
} t_alumno;

El nombre del tipo va con el prefijo t_. A partir de ahí t_alumno es un tipo como int: declarás t_alumno a1, a2; y accedés a los campos con el operador punto. Cada campo se llama miembro o campo en el vocabulario del apunte.

El ; después de la llave de cierre
} t_alumno; lleva punto y coma. Es la única llave de cierre en todo C que lo lleva, y por eso se olvida. Si te falta, el error que tira el compilador aparece en la línea siguiente y no dice nada de la struct: te va a marcar la declaración que venga después. Cuando un error de sintaxis no tenga sentido, mirá tres líneas más arriba si hay un typedef struct sin cerrar.

Punto contra flecha, valor contra referencia: el programa del apunte

Este es el ejemplo central del apunte de la cátedra, compilado y corrido. Es el código del apunte con dos retoques mínimos: el main del apunte está escrito int main() y sin return, acá va int main(void) con su return 0;, y los comentarios están abreviados. La lógica no se tocó:

#include <stdio.h>
#include <string.h>

typedef int t_legajo;
typedef char t_cadena[50];

typedef struct {
    t_legajo legajo;
    t_cadena nombre;
} t_alumno;

/* por REFERENCIA: para modificar se usa la flecha -> */
void modificar_alumno(t_alumno *alumno)
{
    alumno->legajo = 202340;
    strcpy(alumno->nombre, "Juan");
}

/* por VALOR: es una copia, se accede con el punto */
void mostrar_alumno(t_alumno alumno)
{
    printf("Legajo: %d\n", alumno.legajo);
    printf("Nombre: %s\n\n", alumno.nombre);
}

int main(void)
{
    t_alumno alumno1, alumno2;

    alumno1.legajo = 112130;
    strcpy(alumno1.nombre, "Diego");
    mostrar_alumno(alumno1);

    alumno2 = alumno1;              /* copia el registro ENTERO, cadena incluida */
    mostrar_alumno(alumno2);

    alumno2.legajo = 120001;
    strcpy(alumno2.nombre, "Adrian");
    mostrar_alumno(alumno2);

    mostrar_alumno(alumno1);        /* alumno1 no se movio */

    modificar_alumno(&alumno2);
    mostrar_alumno(alumno2);

    return 0;
}

Tres cosas pasan acá y las tres se preguntan:

  1. alumno2 = alumno1; copia el registro entero. Fijate que nombre es un char[50] y aun así viaja en la copia: el arreglo está adentro del struct, no es un puntero a otro lado. Después modificás alumno2 y alumno1 sigue en "Diego". Son dos variables independientes.
  2. mostrar_alumno(alumno1) recibe una copia. Adentro se usa el punto. Si la función modificara alumno.legajo, afuera no cambiaría nada.
  3. modificar_alumno(&alumno2) recibe la dirección. Adentro el parámetro es t_alumno *alumno y se usa la flecha: alumno->legajo = 202340;. Después de la llamada, alumno2 quedó en 202340 / Juan. Ese es el único caso en que una función puede cambiar un struct del que llama.
p->campo es exactamente lo mismo que (*p).campo

Los paréntesis no son opcionales: el punto tiene más precedencia que el asterisco, así que *p.campo se lee como *(p.campo) y no compila. Por eso existe la flecha.

Struct contra arreglo: se comportan al revés

Esta tabla es la que resuelve la mitad de las preguntas conceptuales del tema. Los dos son "varios datos juntos", y en todo lo demás son opuestos:

Las dos formas de declarar la tabla, y por qué conviene la segunda
typedef alumno_t t_alumnos[TAMANIO]; crea un tipo tabla, y entonces la función se declara void cargar(t_alumnos vec). Es lo que hace la cátedra.

La alternativa es void cargar(alumno_t vec[], int cantidad), y para todo lo que no use el arreglo completo es mejor, porque el tipo tabla te obliga a que la cantidad sea siempre TAMANIO. En cuanto la carga termina por corte —"la carga finaliza cuando se ingresa código 0", como pide la entrega de la librería— tenés que arrastrar la cantidad real en una variable aparte. El arreglo no la sabe, y sizeof tampoco te la va a decir adentro de la función.

Tamaño de un struct: no es la suma de los campos

El apunte lo dice con cuidado: "el tamaño de la estructura será como mínimo la suma de los tamaños de los miembros individuales", y aclara que la alineación del compilador "puede añadir padding entre los campos o al final". Eso no es teoría: es medible, y cambia según el orden en que declarás los campos.

#include <stdio.h>

typedef struct {
    char inicial;   /* 1 byte  */
    int  legajo;    /* 4 bytes */
    char letra;     /* 1 byte  */
} t_mal;

typedef struct {
    int  legajo;    /* 4 bytes */
    char inicial;   /* 1 byte  */
    char letra;     /* 1 byte  */
} t_bien;

typedef struct {
    int dia;
    int mes;
    int anio;
} t_fecha;

typedef struct {
    char apellido[36];
    char nombre[36];
    t_fecha nacimiento;
    float sueldo;
} t_empleado;

int main(void)
{
    printf("suma de campos t_mal    = %d\n", 1 + 4 + 1);
    printf("sizeof(t_mal)           = %d\n", (int)sizeof(t_mal));
    printf("suma de campos t_bien   = %d\n", 4 + 1 + 1);
    printf("sizeof(t_bien)          = %d\n", (int)sizeof(t_bien));
    printf("sizeof(t_fecha)         = %d\n", (int)sizeof(t_fecha));
    printf("suma de campos t_emple. = %d\n", 36 + 36 + 12 + 4);
    printf("sizeof(t_empleado)      = %d\n", (int)sizeof(t_empleado));
    return 0;
}

Leelo con atención: los mismos tres campos, distinto orden, 12 bytes contra 8. En t_mal el char inicial obliga a rellenar 3 bytes para que el int quede alineado, y después se rellena de nuevo al final. En t_bien, con el int primero, los dos char entran en el hueco. Y t_empleado, con char[36] dos veces, da exactamente la suma: 88 = 88, porque ahí ningún campo necesita corrimiento.

Consecuencia práctica, y es la única que importa para el examen
Nunca escribas el tamaño de un registro a mano. Ni en un fread, ni en un fwrite, ni en un fseek, ni al calcular cuántos registros tiene un archivo. Siempre sizeof(t_registro). Si en la sección 8 escribís fseek(f, k * 38, SEEK_SET) porque contaste los campos, el archivo se te desalinea desde el primer salto.

Comparar structs: qué no compila y qué compila pero miente

Primero, ==. No es que "no conviene": no compila. Este es el error literal de MSVC sobre if (a1 == a2):

error C2088: el operador integrado '==' no se puede aplicar a un operando de tipo 't_alumno'

Segundo, el atajo que a alguien siempre se le ocurre: comparar los bytes con memcmp. Compila, y da mal:

#include <stdio.h>
#include <string.h>

typedef struct {
    char inicial;   /* 1 byte + 3 de relleno antes del int */
    int legajo;
} t_reg;

int mismo_contenido(t_reg a, t_reg b)
{
    return a.inicial == b.inicial && a.legajo == b.legajo;
}

int main(void)
{
    t_reg x, y;

    memset(&x, 0x00, sizeof(t_reg));   /* relleno en 0x00 */
    memset(&y, 0xFF, sizeof(t_reg));   /* relleno en 0xFF */

    x.inicial = 'A';
    x.legajo = 112130;
    y.inicial = 'A';
    y.legajo = 112130;

    printf("sizeof(t_reg) = %d (1 + 4 = 5 campos utiles)\n", (int)sizeof(t_reg));
    printf("campo a campo: %s\n", mismo_contenido(x, y) ? "IGUALES" : "distintos");
    printf("memcmp:        %s\n", memcmp(&x, &y, sizeof(t_reg)) == 0 ? "IGUALES" : "distintos");
    return 0;
}
sizeof(t_reg) = 8 (1 + 4 = 5 campos utiles)
campo a campo: IGUALES
memcmp:        distintos

Los dos registros tienen exactamente los mismos valores en los dos campos, y memcmp dice que son distintos, porque compara también los 3 bytes de relleno, y en esos bytes los dos registros difieren. Acá el relleno se puso distinto a propósito con los dos memset, para que el efecto sea reproducible; en un programa real es peor, porque nadie inicializa el padding y entonces memcmp da igual o distinto según lo que hubiera en la pila, y el mismo programa puede andar hoy y fallar mañana. La única forma correcta de comparar dos registros es campo por campo, con == los numéricos y con strcmp las cadenas.

Struct como parámetro y como valor de retorno

Devolver un struct es legal y es útil: es la forma limpia de que una función de lectura arme una fecha completa. Mirá cómo queda el ejercicio 1 de la guía usando las dos cosas —leer_fecha() devuelve un t_fecha entero, y anios_que_cumple recibe dos structs por valor porque sólo los consulta:

t_fecha leer_fecha(void)
{
    t_fecha f;

    scanf("%d %d %d", &f.dia, &f.mes, &f.anio);
    return f;      /* se devuelve una COPIA del registro completo */
}

/* ... y en el que llama: */
tabla[i].fecha_nacimiento = leer_fecha();

La regla de decisión es de una línea:

Si la función…Pasá…Y adentro accedés con…
sólo lee el registro (mostrar, comparar, calcular)t_empleado e — por valorpunto: e.legajo
tiene que modificar el registrot_empleado *e y se llama con &empflecha: e->legajo

La tercera fila no tiene & ni flecha, y sin embargo modifica el original: el arreglo viaja por referencia siempre. Es la asimetría de la tabla de más arriba, otra vez.

  • El ; que falta después de } t_alumno;. El error aparece en otra línea.
  • a1 == a2: no compila. Campo por campo, y las cadenas con strcmp.

  • Modificar un struct recibido por valor y esperar que se vea afuera. No pasa nada, y no hay ningún aviso del compilador.
  • & de más en un campo char[] del scanf: scanf("%s", &a.nombre). El nombre del arreglo ya es la dirección.
  • & de menos en un campo numérico: scanf("%d", a.legajo) pasa el valor del legajo como si fuera una dirección y escribe ahí. Es comportamiento indefinido: a veces tumba el programa y a veces —peor— sigue andando y pisa memoria ajena. MSVC sí lo marca en compilación: warning C4477: la cadena de formato '%d' requiere un argumento de tipo 'int *'. Ese warning no se ignora.
  • char nombre[35] para 35 caracteres. Van 35 + 1 para el '\0'. Ojo que la propia guía escribe typedef char t_string[35]; en el ejercicio 1: ahí entran 34 letras, no 35.
  • Perder la cantidad real de la tabla. Un arreglo de 100 registros con 7 cargados no sabe que son 7. Esa variable la llevás vos.
  • Binaria sobre una tabla ordenada por otra clave. Si buscás por apellido, la tabla tiene que estar ordenada por apellido.
  • Hardcodear el tamaño del registro. Siempre sizeof: mirá los 12 contra 8 de más arriba.

La clase de Bianchi define archivo como "una colección de información (datos relacionados entre sí), almacenados como una unidad en un dispositivo", y arranca con dos clasificaciones que después se preguntan:

La b no es decorativa: 25 bytes contra 24

En Windows, un archivo abierto sin la b está en modo texto, y ahí la biblioteca traduce cada '\n' (0x0A) que escribís a la pareja '\r''\n' (0x0D 0x0A). Sobre datos binarios eso es corrupción: cualquier byte 0x0A que caiga adentro de un int o de un float agrega un byte fantasma y desalinea todo lo que sigue.

Regla sin excepciones
Archivo de registros → "rb", "wb", "ab", "r+b". Archivo de texto → "r", "w", "a" (la cátedra también escribe "rt", que es lo mismo que "r"). Si el sizeof aparece en tu programa, la b va sí o sí.

El chequeo de apertura que la cátedra exige

Los ocho programas de ejemplo de la cátedra tienen el mismo esqueleto, sin excepción:

    printf("\nNo se pudo abrir el archivo!\n");
else
{
    /* todo el procesamiento va ACA adentro */

Fijate dónde queda el fclose: adentro del else. En dos de los ocho ejemplos —los de fgetc y fgets— la cátedra lo dejó afuera, y con eso, si el archivo no existe, se llama fclose(NULL). La variante equivalente y más cómoda cuando hay varios archivos es salir temprano:

f = fopen("entrada.dat", "rb");
if (f == NULL) {
    printf("No se pudo abrir entrada.dat\n");
    return 1;

El orden de las aperturas cuando hay entrada y salida
Abrí y validá primero las entradas, y recién después la salida. Si abrís fopen("salida.dat", "wb") antes de comprobar que la entrada existe, ya truncaste la salida aunque después abandones con return 1. Y en cada return temprano cerrá lo que ya hayas abierto.

Binarios: fwrite y fread

La cátedra las presenta con esta firma y este ejemplo, textual:

fread ( puntero, tamaño, cantidad, dir_archivo )  ·  fwrite ( puntero, tamaño, cantidad, dir_archivo )
fread  ( &registro, sizeof(registro), 1, archivo );
fwrite ( &registro, sizeof(registro), 1, archivo );
ParámetroQué es
punteroDirección desde la cual tomar (o donde dejar) la información. Por eso lleva &: es &registro, no registro
tamañoCantidad de bytes de un elemento. Siempre sizeof(t_registro), nunca un número escrito a mano
cantidadCuántos elementos. Casi siempre 1; si le pasás n con un arreglo, escribe o lee los n de una
dir_archivoEl FILE *

Y el dato que resuelve medio parcial: las dos devuelven la cantidad de ELEMENTOS leídos o grabados, no bytes ni un booleano. Si pediste 1, te devuelven 1 si pudo y 0 si no. Nunca devuelven EOF. Comparar contra EOF (que vale −1) da verdadero para siempre y arma un ciclo infinito.

El fin de archivo: dónde está exactamente el error clásico

Acá hay que ser preciso, porque "no uses feof" está mal dicho y la cátedra sí usa feof en sus dos ejemplos. El problema no es la función: es dónde ponés la lectura.

Qué hace feof, con precisión
feof(f) devuelve distinto de cero después de que una lectura haya fallado por llegar al final. No devuelve verdadero cuando quedan cero bytes por leer. Es decir: leíste el último registro con éxito → feof sigue en 0. Recién la lectura siguiente, la que falla, enciende el indicador.

De ahí salen las tres versiones. Las corrí las tres sobre el mismo archivo de 3 productos:

Por qué el mal patrón repite el último y no imprime basura
El fread que falla no modifica el búfer de destino: la variable p queda con lo que tenía de la vuelta anterior. Por eso salen dos 103 Regla 30cm y no un registro con valores absurdos. Justamente porque parece un dato válido, el error pasa desapercibido: en un listado de 500 registros, uno repetido al final no se ve. En un total acumulado, sí: te da mal por el último registro.

Acceso directo: fseek, ftell, rewind

FunciónQué hace
fseek(f, desplazamiento, origen)Mueve el puntero del archivo. El desplazamiento va en BYTES y es long. Orígenes: SEEK_SET (inicio), SEEK_CUR (posición actual), SEEK_END (final)
ftell(f)Devuelve la posición actual, en bytes desde el inicio
rewind(f)Vuelve al inicio y limpia los indicadores de fin de archivo y de error. Equivale exactamente a fseek(f, 0L, SEEK_SET) más clearerr(f). Ojo: el de fin de archivo ya lo limpia el fseek; lo que agrega rewind es el clearerr
registro k (base 0) → fseek(f, (long)k * sizeof(t_reg), SEEK_SET)
cantidad de registros → fseek(f, 0L, SEEK_END); cant = ftell(f) / sizeof(t_reg); rewind(f);

    float cantidad;

long cantidad_registros(FILE *f)
{
    long bytes;

    fseek(f, 0L, SEEK_END);      /* me paro al final */
    bytes = ftell(f);            /* ftell dice cuantos bytes tiene */
    rewind(f);                   /* vuelvo al inicio y limpio el flag de EOF */
    return bytes / (long)sizeof(t_regProducto);
}

int leer_registro(FILE *f, long k, t_regProducto *p)
{
    /* el desplazamiento va en BYTES: k * sizeof(registro) */
    if (fseek(f, k * (long)sizeof(t_regProducto), SEEK_SET) != 0)
        return 0;
    return fread(p, sizeof(t_regProducto), 1, f) == 1;
}

El error de fseek, y una precisión que se pregunta mal
1. El error. fseek(f, k, SEEK_SET) te posiciona en el byte k, o sea en la mitad del primer registro. Va multiplicado por sizeof.

2. La precisión. Después de que un fread falla, el indicador de fin de archivo queda encendido — pero un fseek exitoso lo apaga. Lo dice el estándar (C11 §7.21.9.2: "clears the end-of-file indicator for the stream") y está verificado con MSVC: después de agotar un archivo de 3 registros, feof da 1; después de fseek(f, 0L, SEEK_SET) da 0 y la relectura devuelve los 3 registros de nuevo. O sea: para volver a recorrer, fseek al inicio alcanza. Lo que fseek no limpia es el indicador de error; ése sólo lo apagan clearerr y rewind. Por eso rewind sigue siendo la opción recomendable: es fseek al inicio más clearerr en una sola llamada.

Por qué fgetc va en un int y no en un char
fgetc devuelve 0 a 255 para un byte válido, o EOF, que vale −1. Son 257 valores distintos: no entran en un char. Con MSVC el char es con signo, así que el byte 0xFF se guarda como −1 y se confunde con EOF.

La prueba de arriba corre sobre un archivo de 8 bytes que tiene un 0xFF en la posición 3: la versión con char corta a los 3 bytes, la versión con int lee los 8. El ejemplo de la cátedra declara char caracter; y anda sólo porque el archivo de prueba es ASCII puro.

Corte de control: el patrón que arma los últimos tres ejercicios de la guía

"El archivo está ordenado por X" es la señal. Significa que todos los registros de un mismo X vienen juntos, y entonces se puede resumir cada grupo con un solo recorrido y sin arreglos, aunque el archivo no entre en memoria. El esqueleto es siempre éste:

hay = fread(&reg, sizeof(t_reg), 1, entrada);   /* lectura adelantada */

while (hay == 1) {
    clave = reg.campo_clave;      /* arranca un grupo */
    acumulador = 0;
    contador = 0;

    while (hay == 1 && reg.campo_clave == clave) {
        acumulador = acumulador + reg.valor;
        contador++;
        hay = fread(&reg, sizeof(t_reg), 1, entrada);   /* leer al FINAL */
    }

    /* CORTE: cerrar el grupo. El registro que lo rompio YA esta en memoria */
    informar(clave, acumulador, contador);
    if (contador > maximo) { maximo = contador; guardar(clave); }
}
El error que arruina el corte de control
Volver a leer después del ciclo interno. El registro que hizo cortar ya se leyó y está en la variable: si leés otra vez, te salteás el primer registro de cada grupo. El síntoma es que todos los grupos quedan con un registro de menos y el primero de cada uno desaparece del listado.

El otro: comparar la clave con == cuando es una cadena. Ahí va strcmp(reg.patente, clave) == 0, y para guardarla, strcpy.

Las trampas de archivos, en orden de frecuencia

  • while (!feof(f)) con la lectura al principio del cuerpo: procesa el último registro dos veces. Verificado más arriba: 4 vueltas sobre 3 registros.
  • Comparar fread contra EOF. fread devuelve 0 o la cantidad de elementos; nunca −1. 0 != EOF es verdadero: ciclo infinito.
  • Abrir con "w" un archivo que querías conservar: queda en cero bytes con sólo abrirlo.
  • Olvidar la b en un archivo de registros: 25 bytes donde iban 24, y los datos vuelven cambiados sin ningún error.
  • No validar if (f == NULL): la primera operación sobre el puntero nulo tumba el programa.
  • Abrir la salida antes de validar las entradas: la truncaste aunque después abandones.
  • fseek con el desplazamiento en registros en vez de bytes.
  • No volver al principio antes de recorrer un archivo por segunda vez: el puntero quedó en el final y no leés nada. Va rewind(f) (o fseek(f, 0L, SEEK_SET), que también apaga el indicador de fin de archivo).
  • fgetc guardado en un char: con el byte 0xFF corta antes de tiempo.
  • fgets y el '\n' que se guarda adentro de la cadena, que después rompe el strcmp.
  • fflush(stdin): comportamiento indefinido. Anda en la consola de MSVC y no anda en ningún otro lado.
  • Hardcodear el tamaño del registro en vez de sizeof: el padding te lo cambia (sección 7).
  • Olvidar el fclose: lo que quedó en el búfer no llega al disco y el archivo sale incompleto.

Esa es la definición formal y sirve para reconocer una función recursiva cuando la ves. Para escribir una, la diapositiva que importa es otra: la que enumera los tres elementos que el flujo de control necesita para funcionar. La cátedra los lista así, textual:

Los tres elementos obligatorios
  • "Una evaluación para detener o continuar la recursión."
  • "Una llamada recursiva para continuar la recursión."
  • "Un caso final para terminar la recursión (caso base)."
Si tu función no tiene los tres, no funciona. La pila de llamadas, dibujada de verdad

Esto es lo que más se pregunta y lo que menos se entiende: qué pasa exactamente cuando una función se llama a sí misma. Compilamos un factorial instrumentado que imprime cada entrada y cada salida, con sangría por nivel de profundidad:

#include <stdio.h>

int nivel = 0;

void sangrar(void)
{
    int i;

    for (i = 0; i < nivel; i++)
        printf("  ");
}

long long factorial(int n)
{
    long long resultado;

    sangrar();
    printf("-> entra factorial(%d)\n", n);
    nivel++;
    if (n <= 1) {
        nivel--;
        sangrar();
        printf("<- caso base: factorial(%d) devuelve 1\n", n);
        return 1;
    }
    resultado = n * factorial(n - 1);
    nivel--;
    sangrar();
    printf("<- sale  factorial(%d) devuelve %d * %lld = %lld\n", n, n, resultado / n, resultado);
    return resultado;
}

int main(void)
{
    printf("factorial(4) = %lld\n", factorial(4));
    return 0;
}

      -> entra factorial(1)

Leelo en dos fases, porque son dos fases
Fase de bajada (las flechas →): cada llamada apila un marco nuevo en el stack con sus parámetros y sus variables locales, y queda congelada en la línea del return esperando el resultado de la siguiente. Cuatro llamadas activas al mismo tiempo, cuatro copias de n y de resultado vivas en memoria: n vale 4, 3, 2 y 1 simultáneamente, cada una en su marco.

Fase de subida (las flechas ←): arranca cuando una llamada devuelve sin llamarse a sí misma —el caso base—. Ahí se desapilan los marcos en orden inverso, y recién ahí se calculan las multiplicaciones: 2·1, después 3·2, después 4·6. La cuenta se hace de adentro para afuera, al revés del orden en que la escribiste.

El error de lectura clásico es creer que n * factorial(n - 1) multiplica y después llama. Es al revés: primero se resuelve la llamada entera, hasta el fondo, y con el valor que vuelve se multiplica.

indirecta_double.c(11): error C2371: 'es_impar': nueva definición; tipos básicos distintos
Qué escribir en el parcial: la declaración implícita se eliminó del lenguaje en C99; hoy es una violación del estándar y gcc 14 en adelante la rechaza directamente como error. Que MSVC la acepte con un warning es una concesión de compatibilidad hacia atrás, no C válido. El prototipo adelantado va siempre, y en la recursión indirecta es el único orden de escritura posible.

Recursión múltiple: los dos ejemplos de la cátedra en un programa

Los ejemplos 02 (Combinatoria) y 05 (Mostrar Pares) del campus, compilados juntos. La combinatoria es recursión múltiple con dos casos base; mostrar pares es recursión simple que no devuelve nada:

int combinatoria(int n, int m)
{
    if (m == 0 || m == n)
        return 1;
    return combinatoria(n - 1, m - 1) + combinatoria(n - 1, m);
}

void mostrar_pares(int n)
{
    if (n < 2)
        return;
    mostrar_pares(n - 1);
    if (n % 2 == 0)
        printf("%d ", n);
}

La combinatoria tiene dos casos base y los dos son necesarios
Con m == 0 solo, la llamada combinatoria(n - 1, m) nunca baja m y se cuelga cuando m > n. Con m == n solo, la otra rama tampoco corta. Los dos juntos cubren las dos direcciones en que puede bajar el problema.

Y ojo con el dominio: sólo termina si 0 ≤ m ≤ n. Lo compilamos con combinatoria(3, 7) y muere con 0xC00000FD. El motivo exacto conviene tenerlo claro: la rama combinatoria(n - 1, m - 1) sí corta —bajando los dos a la vez, m llega a 0 en (-4, 0)—, pero la rama combinatoria(n - 1, m) deja m fijo en 7 y hace bajar n para siempre: m == 0 nunca va a pasar ahí y m == n se aleja en cada paso. Alcanza con que una sola rama no corte para que el programa reviente. Si el enunciado no garantiza el rango, validalo en main.

Recursión vs iteración: el criterio de la cátedra, textual

La presentación fija la doctrina en dos diapositivas, y conviene citarlas porque es exactamente lo que te van a pedir que justifiques:

Lo que dice la cátedraQué hacés con eso
"Todo problema que se pueda resolver recursivamente, también se puede resolver iterativamente."Nunca digas "esto sólo se puede hacer recursivo". Es falso y la cátedra lo escribió.

La regla de bolsillo

Recursión infinita: qué pasa de verdad

La cátedra dice que "el código se ejecutará hasta que la computadora agote la memoria disponible y se produzca una terminación anormal del programa por desbordamiento de pila (stack overflow)". Lo comprobamos. Este programa:

void hundirse(int n)
{
    profundidad++;
    if (profundidad % 10000 == 0)
        printf("profundidad alcanzada: %d\n", profundidad);
    hundirse(n + 1);
}

Dos resultados concretos, los dos útiles:

  1. El compilador te avisa antes de ejecutar. MSVC tira warning C4717: 'hundirse': recursiva para todas las rutas de acceso de control; la función provocará el desbordamiento de la pila en tiempo de ejecución. Si ves ese warning, tenés la recursión rota: no la ejecutes, arreglala.
  2. Al ejecutar, el programa muere con código de salida 0xC00000FD (-1073741571 en decimal), que es exactamente STATUS_STACK_OVERFLOW de Windows. No devuelve un resultado malo: no devuelve nada. Y las líneas de "profundidad alcanzada" nunca aparecen, porque el buffer de stdout se pierde cuando el proceso aborta.
"Stack overflow" y "memory leak" no son lo mismo y se confunden en el parcial
El desbordamiento de pila es de la sección 9: demasiadas llamadas anidadas, la pila se llena, el programa aborta. La fuga de memoria es de la sección 10: pediste heap con malloc y no lo liberaste, el programa sigue andando y consume cada vez más. Uno mata el proceso al instante; el otro lo envenena de a poco.

El molde: cómo escribir cualquier función recursiva en cuatro pasos

El procedimiento, siempre el mismo
1. ¿Cuál es el caso más chico que sé responder sin pensar? Ese es el caso base, y va primero en la función. ▸ 2. ¿Cómo escribo el problema de tamaño n usando el mismo problema de tamaño menor? Ese es el caso recursivo. ▸ 3. ¿La llamada recursiva se acerca al caso base en cada paso? Si el argumento no baja (o no sube hacia el corte), tenés recursión infinita. ▸ 4. Trazá a mano el caso base y el caso base + 1. Si esos dos dan bien, el resto sale por inducción.

1 · El caso base va antes de la llamada recursiva. Siempre.

Parte I · Punteros

Qué es un puntero, en una línea

La definición del apunte, textual
"Un puntero es un tipo especial de variable que almacena direcciones de memoria."

Eso es todo. Un int guarda un número; un int * guarda dónde está un número. Y como es una variable normal, el puntero también tiene su propia dirección: eso es lo que va a permitir después los dobles punteros.

Compilamos el ejemplo del apunte con las direcciones reales impresas:

int x = 5;
int y = 8;
int *p1;
int *p2;

p1 = &x;
p2 = &y;

printf("x vale %d y vive en %p\n", x, (void *) &x);
printf("p1 vale %p (la direccion de x) y vive en %p\n", (void *) p1, (void *) &p1);
printf("*p1 vale %d\n", *p1);

*p1 = 8;                /* modifica x indirectamente */
*p1 = *p2;              /* copia el CONTENIDO */
p1 = p2;                /* copia la DIRECCION */
x vale 5 y vive en 00000046434FFC60
p1 vale 00000046434FFC60 (la direccion de x) y vive en 00000046434FFC68
*p1 vale 5
Despues de *p1 = 8, x vale 8
Despues de *p1 = *p2, x vale 8 y y vale 8
Despues de p1 = p2, p1 vale 00000046434FFC64 y p2 vale 00000046434FFC64 (apuntan al mismo lugar)
sizeof(int) = 4, sizeof(int *) = 8, sizeof(char *) = 8

El apunte lo dice así: "Hay que tener cuidado porque el operador ∗ tiene distinta funcionalidad según el caso, decimos que está sobrecargado." En la declaración crea el puntero; después de declarado, lo desreferencia. Es el mismo símbolo con dos trabajos, y confundirlos es el error número uno de la unidad.
Un puntero de 64 bits mide 8 bytes, apunte a lo que apunte
Lo verificamos: sizeof(int *) y sizeof(char *) dan 8 en MSVC de 64 bits, aunque sizeof(int) sea 4 y sizeof(char) sea 1. El puntero guarda una dirección, y todas las direcciones miden lo mismo: una palabra de la arquitectura. El tipo al que apunta no cambia su tamaño; cambia dos cosas distintas: cuántos bytes lee al desreferenciar y cuánto avanza al sumarle 1.
Los dos errores de sintaxis que hay que ver a simple vista
1. p1 = x; en vez de p1 = &x;. El apunte lo señala así: "da error al momento de compilar ya que p1 espera una dirección, no el valor de x". Un puntero se asigna con & (o con lo que devuelve malloc), nunca con un valor.

Precisión que conviene tener, porque el apunte se queda corto: lo compilamos y MSVC no lo rechaza. Da warning C4047: '=': 'int *' es distinto en los niveles de direccionamiento indirecto de 'int', arma el ejecutable, y p1 termina valiendo la dirección 0x0000000000000005. Desreferenciar eso revienta el programa. O sea: el error es real y el diagnóstico existe, pero llega como warning, no como error; si compilás ignorando los warnings, este bug pasa. En el parcial escribí que es un error —lo es, el estándar pide diagnóstico para asignar entre tipos incompatibles—, pero en la máquina acordate de leer los avisos.

2. int* p1, p2; no declara dos punteros. Compilamos esto y medimos: 
int *p1, p2;
...
sizeof(p1) = 8, sizeof(p2) = 4
p1 es un puntero (8 bytes), p2 es un int común (4 bytes). El * se pega al identificador, no al tipo. Para dos punteros: int *p1, *p2;. Por eso conviene escribir siempre int *p y no int* p: la primera forma te recuerda dónde vive el asterisco.

Punteros y arreglos: la relación que sostiene toda la unidad

El apunte dice: "como en la variable vec estamos guardando una dirección la podemos pensar como un puntero", con una salvedad importante: es un puntero constante. Podés cambiar los valores del arreglo, pero no podés hacer que vec apunte a otro lado. Compilado:

int vector[5] = {100, 200, 300, 400, 500};
int *p = vector;
char cadena[5] = {'a', 'b', 'c', 'd', 'e'};
char *pc = cadena;
vector[2]   = 300
*(p + 2)    = 300
p[2]        = 300
*(vector+2) = 300
p     apunta a 000000DBA12FFE70
p + 1 apunta a 000000DBA12FFE74  -> avanzo 4 bytes
pc     apunta a 000000DBA12FFE88
pc + 1 apunta a 000000DBA12FFE89  -> avanzo 1 bytes
Despues de p++, *p = 200
Diferencia (&vector[4] - &vector[0]) = 4
Aritmética de punteros: la regla completa en una frase
Sumarle 1 a un puntero lo mueve sizeof(tipo) bytes, no 1 byte.

Las direcciones reales lo prueban: p es int * y de …FE70 pasa a …FE74 (4 bytes); pc es char * y de …FE88 pasa a …FE89 (1 byte). El compilador escala la cuenta por vos, por eso el tipo del puntero importa.

Y la resta de dos punteros del mismo tipo no da bytes: da cantidad de elementos. &vector[4] - &vector[0] da 4, no 16.

De ahí sale la identidad que hay que tener grabada: v[i] es exactamente *(v + i). Los corchetes son azúcar sintáctica sobre la aritmética de punteros. Por eso un int * devuelto por malloc se usa con corchetes sin ningún trámite.

La única diferencia que importa
Estática: "una vez asignada la memoria, el tamaño no puede cambiar" y "no podemos reutilizar la memoria no utilizada". Más rápida.

Con eso se decide siempre: si sabés el tamaño al escribir el programa, arreglo fijo con #define. Si el tamaño lo decide el usuario en ejecución, heap.

Por qué no alcanza con un arreglo "de tamaño n": el error real del compilador

La pregunta obvia es por qué no se escribe simplemente int v[n] con n leído por teclado. Lo compilamos con MSVC:

int n = 5;

Tres errores y no compila. Los arreglos de tamaño variable son opcionales en C11 y MSVC no los implementa. Por eso la cátedra usa #define con tamaños fijos en todas las guías anteriores, y por eso esta unidad existe: malloc es la única forma portable de pedir "n cosas" cuando n se conoce recién en ejecución.

2. malloc pide bytes totales; calloc pide cantidad y tamaño unitario, por separado. Pasarle a calloc un solo argumento no compila; pasarle a malloc dos, tampoco.

Por qué el chequeo de NULL no es paranoia de manual
malloc devuelve NULL cuando no hay memoria, y no aborta el programa: te devuelve NULL y sigue. Si no lo chequeás, la línea siguiente hace *p = valor sobre la dirección 0 y ahí sí el programa muere, pero muchas líneas después de la causa real y sin decirte por qué.

Además hay tres ejercicios de la guía —el 6, el 7 y el 8— donde el enunciado te lo pide explícitamente: "En caso de no poder reservar la memoria, retornar NULL". Ahí no es buena práctica: es la consigna.

realloc: la trampa que no se ve

Todo el mundo cree que realloc "agranda el bloque donde está". Lo medimos imprimiendo las direcciones:

malloc 4 int   -> 000002000A7F97C0, v[0] = 111
realloc 4000   -> 000002000A801DB0, v[0] = 111

Las dos consecuencias, y las dos se cobran
1. La dirección cambió. Si guardaste el puntero viejo en otro lado (otra variable, un campo de un struct, un vector de punteros), ese otro lado ahora apunta a memoria liberada. Después de un realloc exitoso, el puntero original ya no es válido y no hay que liberarlo: realloc ya lo liberó.

2. Nunca escribas v = realloc(v, ...). Si falla, realloc devuelve NULL y el bloque original sigue vivo. Al asignar el NULL sobre v perdés la única referencia al bloque viejo: fuga de memoria garantizada, en la línea que te iba a salvar de la falla. La forma correcta es con auxiliar: 
auxiliar = realloc(vector, nuevo_tamano * sizeof(int));
if (auxiliar == NULL) {
    printf("No se pudo redimensionar. El bloque original sigue siendo valido.\n");
    free(vector);
    return 1;
}
vector = auxiliar;

Fijate en la salida: free(p) no cambia el valor de p. El bloque volvió al sistema pero el puntero sigue guardando la misma dirección, ahora inválida, y el compilador no tiene forma de saberlo. Leer ahí dio 1032215728 en esta corrida y podría dar otra cosa en la próxima, o abortar.

Asignar NULL arregla las dos cosas de una: el chequeo if (p) pasa a dar falso, y un segundo free(p) se vuelve inofensivo, porque la propia cátedra lo aclara en la ficha de free: "si un puntero NULL se pasa como argumento, no se lleva a cabo acción alguna". Sin el NULL, ese segundo free es un doble free, que la cátedra lista como error explícito.
Una afirmación del apunte de la cátedra que conviene tener matizada
El apunte dice: "debemos ser cuidadosos con el uso de la memoria, ya que si no la liberamos no se recupera ni siquiera cuando finaliza el programa", y más abajo "la memoria que no se libere quedará inhabilitada para su uso, aún cuando el programa hubiera finalizado".

En Windows, Linux y macOS modernos eso no es así: cuando el proceso termina, el sistema operativo recupera todas sus páginas, incluido el heap. No hace falta apagar la máquina, y el programa de fuga que corremos más abajo se puede ejecutar cien veces seguidas sin que la máquina pierda memoria.

Por qué igual tenés que liberar, y el motivo es más fuerte que el del apunte: mientras el programa corre, la memoria filtrada no vuelve. Un programa que filtra en un ciclo se come la RAM disponible hasta que el sistema lo mata. Y en un servidor o un sistema embebido que no termina nunca, "el SO lo limpia al salir" no llega nunca a pasar. Liberá siempre. Pero no repitas en un parcial que la memoria se pierde hasta apagar la máquina.

Arreglos dinámicos y matrices dinámicas

Un vector dinámico es una sola línea y se usa con corchetes como cualquier arreglo:

int *vector = malloc(cantidad * sizeof(int));
if (vector == NULL)
    return 1;
...
free(vector);
vector = NULL;

Una matriz es un vector de punteros, y cada puntero es una fila. El apunte lo dibuja así y el algoritmo 1.1 es exactamente éste. Compilado, 4×5:

int **matriz;
int i;
int j;

matriz = malloc(FILAS * sizeof(int *));        /* el vector de punteros */
if (matriz == NULL)
    return 1;
for (i = 0; i < FILAS; i++) {
    matriz[i] = malloc(COLUMNAS * sizeof(int));  /* cada fila */
    if (matriz[i] == NULL) {

            free(matriz[j]);
        free(matriz);
        return 1;
    }
}
...

Las tres cosas que hay que saber de la matriz dinámica
1. La cuenta. Para F filas hay F + 1 malloc y F + 1 free: uno por fila más el del vector de punteros. Si en un examen ves F malloc y F free, faltan los del vector.

2. El orden de liberación es el inverso al de reserva. Primero las filas, después el vector. Si liberás matriz primero, perdés las direcciones de las filas y ya no las podés liberar: fuga de todo el cuerpo de la matriz.

3. El tamaño del primer malloc es sizeof(int *), no sizeof(int). Ese vector guarda punteros (8 bytes cada uno en 64 bits), no enteros. Pedir FILAS * sizeof(int) reserva la mitad y corrompés el heap desde la fila 3. Es el error más difícil de encontrar de toda la unidad porque el programa arranca bien.

La ventaja que menciona el apunte: "podemos crear matrices irregulares, en donde las filas tienen distinta longitud". Cada fila se pide por separado, así que nada obliga a que midan lo mismo. Eso es exactamente lo que pide el ejercicio 10 con las palabras.

Persistencia: la razón por la que existe todo esto

El cierre del apunte es el argumento más importante de la unidad, y es el que justifica los ejercicios 6, 7 y 8:

int *f(void)
{
    int *p;                       /* nace p (en el stack) */

    p = malloc(sizeof(int));      /* nace una variable anonima en el heap */
    ...
    return p;
}                                 /* p muere, pero la anonima sigue viviendo */
Una función puede devolver memoria del heap. No puede devolver memoria del stack
Si adentro de una función escribís int v[10]; y devolvés v, estás devolviendo la dirección de un arreglo que deja de existir apenas la función retorna: el marco de pila se desapila. El puntero que recibe quien llamó ya nace colgante.

Con malloc no pasa: el bloque está en el heap, que no se limpia solo, y sobrevive al retorno. Eso es lo que el apunte llama persistencia de datos.

El precio, que el propio apunte marca: "es fácil olvidarse de liberar la memoria porque la función que la pide no se encarga de liberarla". Cuando una función devuelve memoria dinámica, el free es responsabilidad de quien la llamó. Escribilo en un comentario arriba de la función; es lo que hace la biblioteca estándar.

Las trampas de esta unidad

1 · Pedir bytes cuando querías elementos
malloc(n) para n enteros reserva n bytes, no n enteros. Con n = 10 pedís 10 bytes y entran dos enteros completos: v[2] ocuparía los bytes 8 a 11 y el bloque termina en el 9, así que desde v[2] ya estás escribiendo fuera. Corrupción de heap silenciosa. Siempre malloc(n * sizeof(int)).
2 · Olvidar el + 1 del '\0' en las cadenas dinámicas
malloc(strlen(s)) reserva exactamente las letras y no el terminador. El strcpy escribe un byte más y pisa el heap. Va siempre malloc(strlen(s) + 1). El enunciado 9 de la guía lo dice con un ejemplo, aunque escribe el terminador como '\n' en el texto y como '\0' en el ejemplo: el correcto es '\0'.
3 · Liberar dentro de un ciclo lo que se pidió una sola vez
Un free adentro de un for que corre n veces sobre el mismo puntero es un doble free desde la segunda vuelta. La regla es simétrica: tantos free como malloc, y en el mismo nivel de anidamiento.
4 · El return temprano que se saltea el free
Toda rama de error que hace return después de un malloc exitoso tiene que liberar antes de salir. Es la fuga más común en código que "funciona": no aparece en el camino feliz, sólo cuando algo falla. Fijate en la matriz dinámica de arriba: la rama de error libera las filas que ya pidió y el vector de punteros, antes del return 1.
5 · El & de más en el scanf sobre memoria dinámica
scanf("%d", numero) con numero ya declarado como int * devuelto por malloc es correcto: scanf quiere una dirección y el puntero ya es una dirección. Escribir &numero le pasa la dirección del puntero, no la del entero: scanf pisa el puntero con el número tipeado y a partir de ahí apuntás a una dirección inventada. Lo compilamos: no da ningún error, sólo warning C4477: 'scanf' : la cadena de formato '%d' requiere un argumento de tipo 'int *', pero el argumento variádico 1 tiene el tipo 'int **', y al ejecutar muere con 0xC0000005 —violación de acceso— en el printf siguiente. Mismo razonamiento con alumno->nombre: es un arreglo, ya es una dirección, va sin &.
6 · Sobre el casteo de malloc
El apunte de la cátedra escribe int *p = (int *) malloc(sizeof(int)); con el casteo. En C el casteo es innecesario: la conversión de void * a cualquier puntero es automática, y todos los ejemplos de esta sección compilan sin él. No es un error escribirlo y la cátedra lo usa, así que ponelo si querés seguir su estilo; pero si ves código sin casteo, no está mal. Lo que sí importa es que el casteo es obligatorio en C++, y esta materia no es C++.

Burbujeo: comparar vecinos, pasada tras pasada

El objetivo, en las palabras de la filmina: "Ordenar los elementos del vector, comparando en pasadas sucesivas, aquellos elementos que son adyacentes". El código de la cátedra, escrito con la convención de código de la cátedra:

void ordenar_por_burbujeo(tvec vec, int ml)
{
    int i, j, aux;

    for (i = 1; i < ml; i++)             /* pasos */
        for (j = 0; j < ml - i; j++)     /* comparaciones */
            if (vec[j] > vec[j + 1]) {
                aux = vec[j];            /* intercambio */
                vec[j] = vec[j + 1];
                vec[j + 1] = aux;
            }
}

Lo tracé con el mismo vector de la filmina, {23, 10, 31, 9}, imprimiendo el estado al final de cada paso. Esta es la salida real del programa compilado:

vector inicial:                                23  10  31   9
fin del paso 1 (3 comparaciones acumuladas):  10  23   9  31
fin del paso 2 (5 comparaciones acumuladas):  10   9  23  31
fin del paso 3 (6 comparaciones acumuladas):   9  10  23  31
vector ordenado:                                9  10  23  31
Por qué el ciclo interno va hasta ml - i y no hasta ml - 1
Mirá el paso 1: el 31 viajó hasta la última posición y ahí se quedó. Eso no es casualidad, es la propiedad del método: después del paso i, las últimas i posiciones ya tienen su valor definitivo. Volver a compararlas es trabajo tirado. Por eso el paso 2 hace 2 comparaciones y el 3 hace 1: 3 + 2 + 1 = 6, que es el número que salió impreso.

La filmina lo resume así: "Para un vector con N elementos a ordenar, serán necesarios N − 1 pasos, y la cantidad de comparaciones en el paso será igual a N − el Nro del paso". Con N = 4: 3 pasos, y 3 + 2 + 1 = 6 comparaciones.
Comparaciones del burbujeo (siempre, sin importar el orden inicial) = (N − 1) + (N − 2) + … + 1 = N · (N − 1) / 2

Burbujeo optimizado: si una pasada no toca nada, terminaste

La filmina hace la pregunta correcta: "¿Qué sucede si en un paso completo, no hubo ningún intercambio?". Respuesta: que ya está ordenado y las pasadas que faltan son puro aire. El código de la cátedra:

void ordenar_por_burbujeo_optimizado(tvec vec, int ml)
{
    int i, j, aux;
    bool hubo_intercambio = true;

    i = 1;
    while ((i < ml) && hubo_intercambio) {       /* pasos */
        hubo_intercambio = false;
        for (j = 0; j < ml - i; j++)
            if (vec[j] > vec[j + 1]) {
                aux = vec[j];                    /* intercambio */
                vec[j] = vec[j + 1];
                vec[j + 1] = aux;
                hubo_intercambio = true;
            }
        i++;
    }
}

Conté los pasos que hace cada versión, con el mismo vector desordenado y con uno ya ordenado. Salida real:

desordenado {23,10,31,9}
  burbujeo comun      -> 3 pasos, resultado:   9  10  23  31
  burbujeo optimizado -> 3 pasos, resultado:   9  10  23  31
ya ordenado {9,10,23,31}
  burbujeo comun      -> 3 pasos, resultado:   9  10  23  31
  burbujeo optimizado -> 1 pasos, resultado:   9  10  23  31
Qué te dice esa tabla de cuatro líneas
Con el vector desordenado la optimización no ahorró nada (3 pasos contra 3): hubo intercambios en todas las pasadas, así que la bandera nunca quedó en false. Con el vector ya ordenado bajó de 3 pasos a 1.

O sea: la optimización no cambia el peor caso —sigue siendo N·(N−1)/2 comparaciones— y convierte el mejor caso en lineal. Si te preguntan "¿en qué mejora?", la respuesta no es "es más rápido": es "mejora el mejor caso y el caso casi-ordenado, no el peor".
Tres formas de romper la bandera
Inicializarla en false fuera del ciclo: el while no entra nunca y el vector queda como estaba.
Ponerla en false adentro del for de comparaciones en vez de adentro del while de pasos: se pisa en cada comparación y sólo se recuerda la última. Ojo, que el propio .c de la cátedra hace exactamente eso en ordenar_con_seguimiento — ahí es a propósito, porque quiere informar el intercambio comparación por comparación, no cortar el ciclo.
Olvidar el i++: ciclo infinito, porque la bandera se vuelve a poner en true mientras siga habiendo desorden en el tramo 0..ml-i que ya no se achica.

Selección: buscar el mínimo del resto y traerlo

Objetivo, textual de la filmina: "buscando el mínimo elemento entre una posición i y la posición final, e intercambiar el mínimo con el elemento de la posición i".

void ordenar_por_seleccion(tvec vec, int ml)
{
    int i, j, aux, pos_minimo;

    for (i = 0; i < ml - 1; i++) {
        pos_minimo = i;
        for (j = i + 1; j < ml; j++)
            if (vec[j] < vec[pos_minimo])
                pos_minimo = j;
        aux = vec[i];
        vec[i] = vec[pos_minimo];
        vec[pos_minimo] = aux;
    }
}

Inserción: abrir el hueco y meter el elemento

Objetivo: "tomando un elemento y comparándolo contra los anteriores ya ordenados, deteniéndose cuando se encuentra uno menor y entonces es allí donde se inserta, desplazando el resto de los elementos mayores".

void ordenar_por_insercion(tvec vec, int ml)
{
    int i, j, aux;

    for (i = 1; i < ml; i++) {
        aux = vec[i];                    /* preservo el valor */
        j = i - 1;
        while ((j >= 0) && (vec[j] > aux)) {
            vec[j + 1] = vec[j];         /* desplazo el elemento */
            j = j - 1;
        }
        vec[j + 1] = aux;                /* lo dejo en su lugar */
    }
}

Búsqueda lineal (secuencial)

No pide nada: el vector puede estar como quiera. Recorrés hasta encontrar o hasta que se acabe.

#define NO_ENCONTRADO (-1)

int busqueda_lineal(tvec vec, int ml, int p)
{
    int i;

    for (i = 0; i < ml; i++)
        if (vec[i] == p)
            return i;
    return NO_ENCONTRADO;
}

La versión de la cátedra (Ejemplo Solución Búsquedas (MS).c) hace lo mismo sin return temprano, con una bandera:

int busqueda_secuencial(tvector valores, int tamanio, int buscado)
{
    int i = 0, posicion = NO_ENCONTRADO;
    bool encontrado = false;

    /* mientras no se encontro y restan elementos por comparar */
    while (!encontrado && i < tamanio) {
        if (valores[i] == buscado) {
            encontrado = true;
            posicion = i;
        }
        i++;
    }
    return posicion;
}
El orden de las dos condiciones del while no es decorativo
Tiene que ser i < tamanio && vec[i] != p, no al revés. El && de C hace cortocircuito: si la primera es falsa, la segunda no se evalúa. Si las das vuelta, cuando el elemento no está, vec[i] se lee con i == tamanio, o sea fuera del máximo lógico. En la versión de la cátedra el problema no existe porque el índice sólo se toca adentro del cuerpo.

Búsqueda binaria: la que sí tiene precondición

int busqueda_binaria(tvec vec, int ml, int p)
{
    int izq = 0;
    int der = ml - 1;
    int medio;

    while (izq <= der) {
        medio = izq + (der - izq) / 2;
        if (vec[medio] == p)
            return medio;
        if (vec[medio] < p)
            izq = medio + 1;
        else
            der = medio - 1;
    }
    return NO_ENCONTRADO;
}

LA precondición: el vector tiene que estar ordenado por LA CLAVE QUE BUSCÁS
Si no lo está, la binaria no da error, no avisa, no cuelga: devuelve mal, y a veces devuelve bien por casualidad, que es peor. Corrí las dos búsquedas sobre el vector sin ordenar {23, 10, 31, 9}. Salida real:

Por qué izq + (der - izq) / 2 y no (izq + der) / 2
Las dos dan el mismo número mientras los índices sean chicos. La diferencia aparece cuando izq + der se pasa de INT_MAX: ahí la suma desborda. Y desbordar un int con signo es, para el estándar, comportamiento indefinido: no hay ningún resultado prometido. En la práctica, en MSVC y en gcc sobre x86-64, el valor da la vuelta y sale negativo — y vec[negativo] lee fuera del arreglo. El .c de la cátedra lo escribe así y deja el comentario: "evitamos overflow de la suma directa". Con vectores de 20 elementos jamás pasa; se escribe igual, porque es gratis y porque es la forma que el corrector reconoce.

La variante de la cátedra: cortar por rango en vez de por izq > der

El archivo Ejemplo Solución Búsquedas (MS).c no usa while (izq <= der). Usa una bandera y descarta primero por rango:

while (!terminado) {
    if ((buscado < valores[inf]) || (buscado > valores[sup])) {
        terminado = true;                    /* NO ESTA => FIN DE LA BUSQUEDA */
        posicion = NO_ENCONTRADO;
    } else {
        mit = inf + ((sup - inf) / 2);       /* evitamos overflow de la suma directa */
        if (valores[mit] == buscado) {
            terminado = true;                /* ENCONTRADO => FIN DE LA BUSQUEDA */
            posicion = mit;
        } else if (buscado > valores[mit]) {
            inf = mit + 1;
        } else {
            sup = mit - 1;
        }
    }
}

Es correcta, y el if del rango no es un adorno: es lo único que impide que inf o sup se salgan del arreglo. En esta versión el while no chequea inf <= sup, así que si sacás ese if el ciclo puede leer valores[-1] o valores[tamanio]. Las dos formas son válidas; elegí una y no las mezcles, que es de donde salen los cuelgues.

#define POR_LEGAJO   2
#define POR_EDAD     3

/* Devuelve <0, 0 o >0 igual que strcmp, segun el criterio elegido. */
int comparar(t_empleado *a, t_empleado *b, int criterio)
{
    int r;

    switch (criterio) {
    case POR_APELLIDO:
        r = strcmp(a->apellido, b->apellido);
        if (r == 0)
            r = strcmp(a->nombre, b->nombre);      /* desempate */
        return r;
    case POR_LEGAJO:
        return a->legajo - b->legajo;
    case POR_EDAD:
        if (a->fecha_nacimiento.anio != b->fecha_nacimiento.anio)
            return a->fecha_nacimiento.anio - b->fecha_nacimiento.anio;
        if (a->fecha_nacimiento.mes != b->fecha_nacimiento.mes)
            return a->fecha_nacimiento.mes - b->fecha_nacimiento.mes;
        return a->fecha_nacimiento.dia - b->fecha_nacimiento.dia;
    }
    return 0;
}

void ordenar(t_tabla tabla, int n, int criterio)
{
    int i, j, pos_minimo;
    t_empleado aux;

    for (i = 0; i < n - 1; i++) {
        pos_minimo = i;
        for (j = i + 1; j < n; j++)
            if (comparar(&tabla[j], &tabla[pos_minimo], criterio) < 0)
                pos_minimo = j;
        aux = tabla[i];                  /* el struct entero se asigna con = */
        tabla[i] = tabla[pos_minimo];
        tabla[pos_minimo] = aux;
    }
}

TDA: tipo de dato abstracto

De dónde sale lo que sigue
La cátedra publica una actividad llamada "TDA" y una tarea llamada "Ejercicio TDA Número Complejo" en la sección "Memoria / Recursividad / TDA" del campus, pero no publica ni la consigna ni material teórico de TDA, y no hay ningún ejercicio de TDA en las 9 guías. Lo que sigue es construcción nuestra a partir del título de esa tarea, con la convención de código de la cátedra. Está compilado y corrido, pero no es palabra de la cátedra.

Un tipo de dato abstracto es un tipo definido por qué operaciones se le pueden hacer, no por cómo está guardado. La diferencia con un struct pelado es de disciplina: en un TDA el que usa el tipo no toca los campos, sólo llama funciones.

La implementación — complejo.c, en coordenadas cartesianas:

#include <stdio.h>
#include <math.h>
#include "complejo.h"

t_complejo complejo_crear(double parte_real, double parte_imaginaria)
{
    t_complejo c;

    c.re = parte_real;
    c.im = parte_imaginaria;
    return c;
}

double complejo_real(t_complejo c)
{
    return c.re;
}

double complejo_imaginaria(t_complejo c)
{
    return c.im;
}

t_complejo complejo_sumar(t_complejo a, t_complejo b)
{
    return complejo_crear(a.re + b.re, a.im + b.im);
}

t_complejo complejo_multiplicar(t_complejo a, t_complejo b)
{
    return complejo_crear(a.re * b.re - a.im * b.im,
                          a.re * b.im + a.im * b.re);
}

double complejo_modulo(t_complejo c)
{
    return sqrt(c.re * c.re + c.im * c.im);
}

/* Se apoya en las observadoras, no en los campos: asi este mismo
   cuerpo sirve tal cual para la implementacion polar de mas abajo. */
void complejo_mostrar(t_complejo c)
{
    if (complejo_imaginaria(c) >= 0)
        printf("%.2f + %.2fi", complejo_real(c), complejo_imaginaria(c));
    else
        printf("%.2f - %.2fi", complejo_real(c), -complejo_imaginaria(c));
}

Las cuatro reglas que hacen que algo sea un TDA y no un struct suelto
1. Toda operación empieza con el nombre del tipo: complejo_crear, complejo_sumar. Es la forma que C tiene de simular espacios de nombres.
2. Hay una constructora (complejo_crear). Nadie arma un valor del tipo campo por campo.
3. Hay observadoras (complejo_real, complejo_modulo) para sacar información sin conocer la representación.
4. El .h lleva guarda de inclusión (#ifndef / #define / #endif). Sin ella el peligro no es que dos .c distintos lo incluyan —eso son dos unidades de compilación separadas y no molesta—: es que un mismo .c lo termine incluyendo dos veces, directo y de rebote a través de otro header. Ahí el typedef struct aparece dos veces en la misma unidad y el compilador corta. Los prototipos repetidos serían legales; el typedef repetido no, porque cada struct { ... } anónimo es un tipo nuevo.

1 · El punto y coma después del if o del for

int nota = 3;
int i;

if (nota >= 4);
    printf("Aprobado con %d\n", nota);

for (i = 0; i < 3; i++);
    printf("i vale %d\n", i);

Salida real:

Aprobado con 3
i vale 3

Dice "Aprobado" con un 3, e imprime una sola vez lo que debía imprimirse tres veces. El ; es una sentencia vacía, y esa sentencia vacía es el cuerpo del if y del for. El printf indentado no pertenece a ninguno de los dos: es la línea que viene después, y se ejecuta siempre.

Por qué éste es el peor de la lista
La indentación te miente. El printf está corrido a la derecha, así que parece el cuerpo. Y MSVC no dice nada ni con /Wall: verificado. Es el error que más tiempo se pasa buscando en el lugar equivocado.

Cómo se busca: cuando un if o un while "no hace caso", mirá el final de la línea de la condición antes que ninguna otra cosa. Es el primer lugar, no el último.

La variante que cuelga: while (i < 10); con el i++ afuera. El cuerpo vacío se repite para siempre sin imprimir nada. Si tu programa se queda mudo, buscá ese punto y coma.

2 · = en vez de ==

int nota = 3;

if (nota = 4)
    printf("Aprobado con nota %d\n", nota);
else
    printf("Desaprobado con nota %d\n", nota);

printf("al salir del if, nota vale %d\n", nota);

Salida real:

Aprobado con nota 4
al salir del if, nota vale 4

Dos daños en una línea. Primero, nota = 4 asigna 4 y la expresión vale 4, que es distinto de cero, o sea verdadero: entra al if pase lo que pase. Segundo, destruye el dato: la nota real (3) se perdió, y todo lo que venga después trabaja con un 4 inventado.

El único caso en que da falso, que es el que te confunde
if (x = 0) nunca entra, porque la asignación vale 0. Entonces te encontrás con que if (nota = 4) "siempre entra" y if (nota = 0) "nunca entra": el if ignora la variable y decide por el valor asignado.

Compilación: con /W3 MSVC no dice nada. Con /W4 sí: warning C4706: asignación usada como condición. Verificado. Si podés, compilá siempre con el nivel de warnings alto.

3 · scanf sin &

int n = 0;

printf("Ingrese un numero: ");
scanf("%d", n);          /* falta el & */
printf("Leiste %d\n", n);

Al compilar (MSVC /W3):

warning C4477: 'scanf' : la cadena de formato '%d' requiere un argumento de tipo 'int *',
               pero el argumento variádico 1 tiene el tipo 'int'

Al ejecutar con la entrada 7: el programa aborta con código 0xC0000409 y no imprime ni siquiera el "Ingrese un numero: ", porque el buffer de salida no llega a vaciarse antes del corte.

Por qué el & y por qué a veces no va
scanf necesita dónde guardar, o sea una dirección. Sin el & le mandás el contenido de n (un 0) y scanf lo interpreta como si fuera una dirección de memoria: escribe el 7 en la dirección 0.

La excepción, y es una sola: con %s sobre un char[] no va el &, porque el nombre de un arreglo ya es la dirección de su primer elemento. scanf("%s", nombre) está bien; scanf("%s", &nombre) también funciona por casualidad (misma dirección, distinto tipo) pero es incorrecto. Y no esperes que el compilador te salve: lo compilé con /W3 y con /W4 y MSVC no dice una palabra de ese & de más. El C4477 salta cuando falta el & en un %d, no cuando sobra en un %s.

La regla de bolsillo: %d, %f, %c, %lf → con &. %s sobre un arreglo → sin &. Y en un struct: scanf("%d", &p.edad) lleva &, scanf("%s", p.nombre) no.

4 · <= en vez de <: desbordar el arreglo

#define MAX 5

int v[MAX];
int i;

for (i = 0; i <= MAX; i++)         /* <= en vez de < */
    v[i] = i * 10;

Este programa corrió sin dar ningún síntoma: imprimió los cinco valores correctos y terminó con código 0. Escribió en v[5], que no existe, y no pasó nada visible. Para ver lo que hace, puse una variable justo al lado en memoria:

struct {
    int v[MAX];
    int centinela;
} d;

d.centinela = 777;
for (i = 0; i <= MAX; i++)
    d.v[i] = i * 10;

Salida real:

v[0] = 0
v[1] = 10
v[2] = 20
v[3] = 30
v[4] = 40
centinela = 50   (valia 777 antes del ciclo)

El ciclo escribió seis valores en un arreglo de cinco. El sexto (50) fue a parar a centinela, que ahora vale cualquier cosa. El error está en el ciclo y el daño aparece en otra variable, quizá cien líneas más abajo. Por eso se busca donde no está.

Un arreglo de N tiene índices 0 a N−1. No hay v[N]. Nunca.
Y el compilador no chequea el índice: verificado, ni con /Wall dice una palabra del desborde. A /Wall aparece una C5045 sobre mitigación de Spectre, que es otra cosa. C confía en vos.

Compilado con /RTC1 (comprobaciones de tiempo de ejecución de MSVC) el mismo programa sí aborta, con código 0x80000003. Si tu IDE compila en modo Debug, probablemente tengas eso activado y el error te salte. En modo Release no.

El único ciclo correcto para recorrer un arreglo es for (i = 0; i < n; i++). Si escribís <=, el tope tiene que ser n - 1. Elegí una forma y usá siempre la misma; mezclar es de donde salen los off-by-one.

5 · Olvidar el terminador nulo

struct {
    char corta[4];
    char resto[10];
} d;

strcpy(d.resto, "BASURA");
strncpy(d.corta, "Hola", 4);       /* 4 caracteres justos: no queda lugar al terminador */

printf("printf(\"%%s\") sobre d.corta imprime: %s\n", d.corta);
printf("strlen(d.corta) devuelve: %d\n", (int) strlen(d.corta));

Salida real:

printf("%s") sobre d.corta imprime: HolaBASURA
strlen(d.corta) devuelve: 10
y d.resto seguia valiendo: BASURA

La cadena "Hola" tiene 4 letras y char corta[4] tiene 4 lugares: entran las letras y no entra el \0. Y una cadena en C no sabe cuánto mide: printf y strlen avanzan hasta encontrar un cero. Como no hay ninguno en corta, siguen leyendo la variable de al lado. Salió HolaBASURA y strlen devolvió 10.

La regla N+1, que es literalmente todo lo que hay que recordar
Para guardar hasta N caracteres necesitás char campo[N + 1]. Si el enunciado dice "Apellido (35 caracteres)", va char apellido[36]. Si dice "patente de 10 caracteres", va char patente[11].

Este error apareció en la revisión de la guía de Struct: una solución declaraba typedef char t_string[35] para un campo de 35 caracteres, mientras otro ejercicio de la misma guía usaba char apellido[36] para el mismo campo. Con [35] el apellido se trunca a 34 letras en silencio.

Y la consecuencia práctica: strncpy no agrega el terminador si la fuente llena el destino. strcpy sí lo agrega, pero no controla el tamaño. Si usás strncpy, poné el \0 a mano: destino[N] = '\0';

6 · while (!feof(f)): el último registro sale dos veces

Escribí un archivo binario con tres enteros —10, 20 y 30— y lo leí de las dos formas en el mismo programa.

/* mal */
while (!feof(f)) {
    fread(&n, sizeof(int), 1, f);
    printf("%d ", n);
}

/* bien */
while (fread(&n, sizeof(int), 1, f) == 1)
    printf("%d ", n);

Salida real:

-- con while (!feof(f)) --
10 20 30 30
-- con while (fread(...) == 1) --
10 20 30

El 30 aparece dos veces. La razón es de cronología: feof no dice "el próximo fread va a fallar", dice "el fread anterior ya se topó con el final". Después de leer el 30 el archivo está agotado pero la bandera todavía no está prendida; el while da una vuelta más, el fread falla, no toca n —que sigue valiendo 30— y el printf lo imprime de nuevo.

La forma correcta es una sola y sirve para todo
La condición del ciclo es el valor que devuelve la función de lectura.
Binario: while (fread(&reg, sizeof(reg), 1, f) == 1)
Texto con formato: while (fscanf(f, "%d", &n) == 1)
Texto por líneas: while (fgets(linea, TAM, f) != NULL)
Carácter a carácter: while ((c = fgetc(f)) != EOF) — y c tiene que ser int, no char. fgetc devuelve 256 valores de byte más el EOF, y en un char no entran los 257: si el char es sin signo, el EOF (−1) nunca coincide y el ciclo no termina; si es con signo —el caso de MSVC en x64—, el byte 0xFF se vuelve −1 y el ciclo corta de más, en el medio de un archivo binario
Y ojo, porque acá el material de la cátedra no te ayuda: el archivo PDF Lectura TXT - Ejemplo de uso fgetc (GB) escribe char caracter; y while (caracter != EOF), y el comentario de arriba dice char fgetc(FILE *archivo). fgetc devuelve int, no char. Sobre un .txt común el ejemplo anda; el día que el archivo tenga un byte 0xFF, no.

feof sirve después del ciclo, para distinguir "terminó bien" de "hubo un error de lectura".

7 · No chequear el retorno de fopen

f = fopen("no_existe_este_archivo.dat", "rb");
printf("fopen devolvio %s\n", f == NULL ? "NULL" : "un puntero valido");
printf("ahora leo sin haber chequeado...\n");
fflush(stdout);
fread(&n, sizeof(int), 1, f);
printf("esta linea no se llega a imprimir\n");

Salida real:

fopen devolvio NULL
ahora leo sin haber chequeado...

Y ahí termina: el programa abortó con código 0xC0000409. La tercera línea nunca se imprimió.

f = fopen("datos.dat", "rb");
if (f == NULL) {
    printf("ERROR: no se pudo abrir datos.dat\n");
    return 1;
}
Los tres descuidos alrededor de fopen que salieron en la revisión de Struct y Archivos
a) Abrir la salida antes de validar las entradas. Si abrís los tres archivos y recién después chequeás, el fopen(..., "wb") del archivo de salida ya lo creó y lo vació. Aunque después hagas return 1, el archivo de salida quedó destruido. Validá las entradas primero; abrí la salida al final.
b) Irse por return sin cerrar lo que ya abriste. En cada return de error va el fclose de todo lo que esté abierto en ese punto.
c) "w" cuando querías "a". El modo "w" trunca el archivo a cero bytes apenas lo abre, exista o no. Si el enunciado dice "agregar al archivo", el modo es "a".

8 · No chequear el retorno de malloc

v = (int *) malloc((size_t) -1);          /* pedido imposible */
printf("malloc devolvio %s\n", v == NULL ? "NULL" : "un bloque");
printf("ahora escribo sin haber chequeado...\n");
fflush(stdout);
v[0] = 5;

Salida real:

malloc devolvio NULL
ahora escribo sin haber chequeado...

Y abortó con 0xC0000005, que es la violación de acceso clásica: escribir en la dirección NULL.

v = (int *) malloc(n * sizeof(int));
if (v == NULL) {
    printf("ERROR: no hay memoria\n");
    return 1;
}
Tres cosas del malloc que la revisión de Memoria marcó
1. El tamaño se calcula con sizeof, nunca a mano. malloc(n * sizeof(int)), no malloc(n * 4). Y para un vector de n enteros hacen falta n * sizeof(int) bytes: si pedís 10 bytes, entran dos enteros y medio, así que v[2] ya escribe afuera.
2. Con realloc, guardá el resultado en una variable aparte. Si escribís v = realloc(v, mas) y falla, realloc devuelve NULL, vos pisás v con NULL y perdiste el bloque anterior: no lo podés ni usar ni liberar.
3. Un malloc, un free. Ni cero ni dos.

9 · Liberar dos veces el mismo bloque

v = (int *) malloc(4 * sizeof(int));
if (v == NULL)
    return 1;
v[0] = 7;
printf("v[0] = %d\n", v[0]);
free(v);
printf("primer free: ok\n");
fflush(stdout);
free(v);                                   /* segundo free del mismo bloque */

Salida real:

v[0] = 7
primer free: ok

Abortó con 0xC0000374, que es el código de corrupción del heap. El primer free devolvió el bloque; el segundo intentó devolver un bloque que ya no le pertenece al programa y rompió las estructuras internas del administrador de memoria.

La costumbre que lo evita, y que cuesta una línea
free(v);
v = NULL;
free(NULL) está definido y no hace nada. Con esa línea, un segundo free es inofensivo, y además cualquier v[0] posterior falla de inmediato y de forma reproducible en vez de leer memoria liberada (que a veces "anda" y a veces no, según lo que el sistema haya puesto ahí mientras tanto).

Los otros dos de la familia: liberar un puntero que nunca pasó por malloc (por ejemplo el nombre de un arreglo automático) revienta igual; y usar el puntero después del free es un error que no siempre se manifiesta, que es lo que lo hace peor.

10 · Devolver la dirección de una variable local

int *crear_numero(void)
{
    int x = 42;

    return &x;                                 /* la direccion de una local */
}

void otra_funcion(void)
{
    int basura[4] = {111, 222, 333, 444};

    printf("otra_funcion piso la pila con %d...\n", basura[0]);
}

int main(void)
{
    int *p;

    p = crear_numero();
    otra_funcion();
    printf("*p vale %d\n", *p);
    return 0;
}

Al compilar, MSVC /W3 avisa: warning C4172: dirección de devolución de variable local o temporal : x.

Salida real, tres corridas del mismo ejecutable, sin recompilar:

*p vale -1651086763
*p vale -1319075014
*p vale 200066024

Nunca 42, y un número distinto cada vez. La variable x vive en el marco de pila de crear_numero, que deja de existir cuando la función termina. El puntero queda apuntando a un pedazo de pila que la siguiente llamada reutiliza para sus propias variables.

Lo mismo con arreglos y cadenas, que es donde más aparece
char *saludo(void)
{
    char mensaje[20];        /* automatico: muere al volver */

    strcpy(mensaje, "hola");
    return mensaje;          /* MAL */
}
Las tres formas correctas de devolver algo que sobreviva:
1. Que el llamador ponga el espacio y la función lo llene: void saludo(char *destino).
2. Reservar con malloc adentro y que el llamador lo libere — documentándolo, porque si nadie lo libera hay pérdida de memoria.
3. Devolver el struct por valor. En C esto es legal y se copia entero: t_complejo complejo_crear(...) devuelve una copia, no una dirección. Es lo que hace el TDA de la sección 11.

11 · == para comparar cadenas

char a[20] = "hola";
char b[20] = "hola";

if (a == b)
    printf("con == : son iguales\n");
else
    printf("con == : son distintas\n");

if (strcmp(a, b) == 0)
    printf("con strcmp : son iguales\n");
else
    printf("con strcmp : son distintas\n");

printf("a apunta a %p y b apunta a %p\n", (void *) a, (void *) b);

Salida real:

con == : son distintas
con strcmp : son iguales
a apunta a 000000B4B29BFBF8 y b apunta a 000000B4B29BFBE0

Las dos cadenas dicen exactamente lo mismo y el == dice que son distintas. La última línea explica por qué: el nombre de un arreglo, en una expresión, es la dirección de su primer elemento. El == comparó ...FBF8 contra ...FBE0, dos direcciones distintas. Nunca miró el contenido.

strcmp devuelve 0 cuando son IGUALES, y eso lee al revés
if (strcmp(a, b) == 0)        /* iguales   */
if (strcmp(a, b) != 0)        /* distintas */
if (strcmp(a, b) < 0)         /* a va antes que b alfabeticamente */
Escribir if (strcmp(a, b)) a secas significa "si son distintas", que es lo contrario de lo que la lectura sugiere. Escribí siempre el == 0 explícito.

Y el mismo error al asignar: a = b; con dos char[] ni siquiera compila. Para copiar una cadena es strcpy(a, b). Compara con strcmp, copiá con strcpy, medí con strlen, pegá con strcat — y todas necesitan #include <string.h>.

Ojo con los acentos: strcmp compara byte a byte. Si el enunciado dice "Córdoba" y vos escribís "Cordoba", la comparación da siempre distinto y el contador queda en cero sin ningún síntoma visible. Salió en la revisión de la guía de Struct.

12 · Confundir el máximo físico con el máximo lógico

#define MAX 10

int v[MAX] = {0};
int ml = 4;

v[0] = 23; v[1] = 10; v[2] = 31; v[3] = 9;

for (i = 0; i < MAX; i++)          /* recorre el maximo FISICO */
    suma_mal += v[i];
for (i = 0; i < ml; i++)           /* recorre el maximo LOGICO */
    suma_bien += v[i];

Salida real:

promedio con MAX  (10 posiciones): 7.30
promedio con ml   (4 datos reales): 18.25

El promedio bueno es 18,25 y el malo es 7,30: menos de la mitad. Y el programa no falla: da un número plausible, y por eso pasa el control de "anda". Acá el vector estaba inicializado en ceros; si no lo estuviera, las seis posiciones sobrantes tendrían basura y el promedio sería cualquier cosa, distinta en cada corrida.

Los dos números y la regla
El físico es la constante del #define: cuántas posiciones existen. El lógico es el parámetro que viaja al lado del vector: cuántas tienen datos.

La constante aparece exactamente una vez en tu programa: en el typedef o en la declaración. En cualquier otro lugar donde la escribas, parate. Es también el error del máximo lógico en las funciones: si pasás el vector sin pasar ml, la función no tiene forma de saber dónde terminan los datos, porque sizeof sobre un parámetro arreglo devuelve el tamaño de un puntero, no del arreglo.

13 · int *p1, p2; declara un puntero y un entero

int *p1, p2;                 /* p1 es puntero a int; p2 es un int comun */
int x = 5;

p1 = &x;
p2 = &x;
printf("*p1 = %d\n", *p1);
printf("p2 (que NO es puntero) vale %d\n", p2);

Al compilar: warning C4047: '=': 'int' es distinto en los niveles de direccionamiento indirecto de 'int *'. Salida real:

*p1 = 5
p2 (que NO es puntero) vale 1039136736

El * se pega al declarador, no al tipo. int *p1, p2; es int *p1; y int p2;. El valor 1039136736 son los 32 bits bajos de una dirección de 64 bits, truncada al meterla en un int.

Escribí un puntero por línea
int *p1;
int *p2;
Es la única forma de no equivocarse, y es lo que hace el material de la cátedra. Si querés dos en la misma línea, el * va repetido: int *p1, *p2;

De la misma familia: printf("%d", p) con p un int * no imprime la dirección: en 64 bits el puntero mide 8 bytes y %d lee 4. Para imprimir una dirección es printf("%p", (void *) p);

14 · El scanf que falla y deja la basura en el buffer

do {
    printf("Ingrese la cantidad (1 a 100): ");
    leidos = scanf("%d", &n);
    printf("  [scanf devolvio %d]\n", leidos);
} while (n < 1 || n > 100);

Corrido con la entrada abc (y con un freno de seguridad en la vuelta 5 para que se pudiera ver la salida). Salida real:

Ingrese la cantidad (1 a 100):   [scanf devolvio 0]
Ingrese la cantidad (1 a 100):   [scanf devolvio 0]
Ingrese la cantidad (1 a 100):   [scanf devolvio 0]
Ingrese la cantidad (1 a 100):   [scanf devolvio 0]
Ingrese la cantidad (1 a 100):   [scanf devolvio 0]
  ... corto a mano en la vuelta 5: sin este freno no para nunca

Ciclo infinito. Cuando scanf("%d") se encuentra con texto, devuelve 0, no toca n y —esto es lo clave— no consume la entrada: las letras siguen ahí para la vuelta siguiente, que vuelve a fallar exactamente igual. Y en la primera vuelta n está sin inicializar, así que la condición del while lee basura.

int leidos;
int c;

do {
    printf("Ingrese la cantidad (1 a 100): ");
    leidos = scanf("%d", &n);
    if (leidos != 1) {
        while ((c = getchar()) != '\n' && c != EOF)
            ;                          /* descarto lo que quedo en el buffer */
        n = 0;                         /* valor invalido, obliga a repetir */
    }
} while (n < 1 || n > 100);
El primo hermano: el \n que queda después de un scanf("%d")
Si hacés scanf("%d", &edad) y a continuación scanf("%c", &letra), la letra se lleva el Enter que quedó en el buffer, sin darle al usuario la chance de escribir. La solución entra en una tecla: un espacio adelante del formato, scanf(" %c", &letra). Ese espacio significa "salteá todos los blancos que haya antes". Esto no sale de ningún PDF de la cátedra —el material publicado no usa %c con scanf en ningún lado—: es la solución estándar de C, y funciona.

15 · fgets con el tamaño justo: la lectura siguiente se saltea

#define LARGO_ORACION 50

typedef char t_oracion[LARGO_ORACION + 1];   /* char[51] */

void leer_oracion(t_oracion destino)
{
    int largo;

    fgets(destino, LARGO_ORACION + 1, stdin);      /* lee a lo sumo 50 caracteres */
    largo = (int) strlen(destino);
    if (largo > 0 && destino[largo - 1] == '\n')
        destino[largo - 1] = '\0';
}

Corrido con una primera oración de exactamente 50 caracteres y una segunda cualquiera. Salida real:

oracion 1 = [AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA] (50 caracteres)
oracion 2 = [] (0 caracteres)

La segunda oración quedó vacía: el usuario nunca pudo escribirla. fgets(s, n, stdin) lee a lo sumo n - 1 caracteres. Con n = 51 lee los 50, corta antes del \n, el if no lo encuentra —el último carácter es una letra— y nadie lo limpia. El fgets siguiente se come ese \n huérfano y devuelve una línea vacía.

typedef char t_oracion[LARGO_ORACION + 2];   /* 50 chars + '\n' + '\0' */

void leer_oracion(t_oracion destino)
{
    int largo;

    if (fgets(destino, LARGO_ORACION + 2, stdin) == NULL) {
        destino[0] = '\0';
        return;                        /* EOF: fgets NO toca el destino */
    }
    largo = (int) strlen(destino);
    if (largo > 0 && destino[largo - 1] == '\n')
        destino[largo - 1] = '\0';
    else
        while (getchar() != '\n' && !feof(stdin))
            ;                          /* el usuario se paso: descarto el sobrante */
}
Y el fgets sin chequear el retorno
Si llega EOF (redirección de archivo, Ctrl+Z en Windows), fgets devuelve NULL y no escribe nada en el destino. El strlen siguiente corre sobre un arreglo automático sin inicializar: largo puede dar cualquier cosa, y si da más que el tamaño del arreglo, destino[largo - 1] = '\0' escribe afuera. Por eso el if (... == NULL) va antes que el strlen, siempre.

16 · Inicializar el máximo en 0 (y el mínimo en un número grande)

int mayor_mal = 0;

Con la serie -4 -9 -2 -30. Salida real:

serie: -4 -9 -2 -30
con mayor inicializado en 0     -> 0
tomando el primer dato de la serie -> -2

El máximo de una serie de negativos es −2, y la versión con mayor = 0 devuelve 0, un número que no está en la serie. La revisión de la guía de Básicos lo señala como el error más frecuente de toda esa guía.

La forma correcta: el primer dato es el máximo y el mínimo
No inventes un valor inicial. Tomá el primero de la serie, con un contador o una bandera: 
if (cantidad == 0) {
    mayor = num;
    menor = num;
} else if (num > mayor) {
    mayor = num;
} else if (num < menor) {
    menor = num;
}
cantidad++;
El else if encadenado no pierde casos: si num > mayor, entonces seguro num >= menor, así que la segunda comparación nunca hacía falta.

El mismo error, disfrazado: inicializar el mínimo en 0 cuando la serie es de positivos. Y otro pariente: inicializar menor_diferencia = 0 en el ejercicio de Vectores 8 de la sección 11, donde tampoco puede ser 0 salvo que exista una diferencia nula de verdad.

La revisión de 90 segundos, antes de entregar

Este es el orden en que conviene mirar. Los primeros son los que compilan limpio, o sea los que ningún compilador te va a marcar.

  1. Buscá ); al final de cada if, for y while. No hay warning que te salve.
  2. Buscá = solo adentro de un if o un while. Con /W3 tampoco hay warning.
  3. Todos los ciclos de arreglo con < n, ninguno con <= n. Y el n es el máximo lógico.
  4. Todos los scanf numéricos con &; el %s sin &.
  5. Todas las comparaciones de cadenas con strcmp(a, b) == 0. Ningún == entre dos char[].
  6. Todos los char de N caracteres declarados con [N + 1].
  7. Ningún while (!feof(f)). La condición es el retorno de la función de lectura.
  8. Todo fopen y todo malloc con su if (... == NULL) inmediatamente después.
  9. Todo malloc con exactamente un free, y un = NULL al lado.
  10. Ningún return &variable_local ni return arreglo_local.
  11. Ningún máximo inicializado en 0 si la serie puede tener negativos.
  12. Corré el programa con: el caso normal, el caso vacío (cero datos), un solo dato, y un dato inválido. Si no lo corriste con esos cuatro, no lo probaste.
La conclusión de haber compilado todo esto
De los 16 errores, los 16 compilan. Con /W3 sólo tres dan warning (el scanf sin &, el return &local y el int *p1, p2); con /W4 se suma un cuarto (el = adentro del if). Los otros doce compilan en silencio absoluto, incluso con /Wall.

Al ejecutar, cuatro abortan con un código que no dice qué línea fue. Los doce restantes devuelven un resultado equivocado y siguen andando, que es la categoría que hace perder puntos: el programa entrega, corre, no rompe, y el número está mal.

"Compiló" es el piso, no la meta. El único chequeo que sirve es correrlo y mirar el número.
